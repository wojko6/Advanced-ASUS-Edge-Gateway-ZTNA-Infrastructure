## Why coverage is a separate layer from DNS health

The operator explicitly confirmed their **router and Fedora laptop are not powered on around the clock**. Missing telemetry is therefore not evidence of resolver outage, and the software must not automatically claim a planned shutdown either without independent supporting evidence.

Operator-run Fedora loopback-only VictoriaMetrics preflights on 2026-10-29:
- 1h: 55 counted mode_bootstrap samples; 6h: 127; 24h: 641; 7d: 4963. These windows were evaluated at different moments and must not be compared as one atomic snapshot.
- A subsequent six-hour export contained 130 samples from 08:52:36 to 11:12:21 Europe/Warsaw, min adjacent interval 59.8s, max 68.0s, and zero internal gaps exceeding 180s. That did **not** imply six full hours of coverage: the first ~3h40m had no samples.
- A bounded 24h source export contained four chunks and 642 mode_bootstrap samples, with five internal gaps exceeding 180s. The largest was 2026-10-28 22:20:06 -> 2026-10-29 08:52:36 CET (~37,950.8s). Two other gaps were ~2,726.4s and ~2,472.0s. These are absence of *observations*, not an established DNS failure.
- A fixed-evaluation 24h count_over_time parity check found **642 observations per metric for all seven DNS Guard metrics**. A separate seven-series raw export alignment check for a 24h window found 642 samples per metric, **MAX_CROSS_SERIES_SKEW_MS=0**, **ROWS_OVER_5000_MS=0**, **TIMESTAMP_ALIGNMENT=PASS**. These checks cover a 24h range, not 7d source alignment or continuous health.

## V0.6-B1 code contract

- tools/v06_coverage_model.py: pure deterministic **in-memory** analysis of the **seven exact metric suffixes** already used by the merged V0.5 fixed archive. No VictoriaMetrics HTTP client, source reader, direct ASUS contact, authentication state, file I/O, scheduled work, HCC endpoint or runtime UI.
- Caller supplies one of the exact window tokens 1h, 6h, 24h, 7d, an explicit UTC evaluation time in milliseconds, and seven ordered lists of (sample_timestamp_ms, value) pairs. No user-supplied PromQL, arbitrary metric or hostname.
- Strict input checks: seven exact series with bounded size (12,000 samples each); integer millisecond timestamps strictly increasing and inside the requested window; integral finite values; equal counts; at most 5-second per-position timestamp skew; collection time no more than 30 seconds from the reference sample; no future router-reported timestamps. Invalid/malformed/out-of-bound source is **UNKNOWN**, not a healthy/verified claim.
- Time **coverage**, not event reconstruction: produce distinct leading, internal, and trailing TELEMETRY_GAP windows when adjacent evidence is more than 180 seconds apart. Give each gap cause=NOT_DETERMINED. Also report bounded segments of valid sampled telemetry and count invalid state observations. Unknown state breaks a segment. No interpolation across missing data or invalid samples, and **no DNS outage/availability verdict, transition time, auto-classified planned shutdown or event list**.
- Output is sanitized: fixed schema, UTC timestamps, counts, intervals and explicit limitations only; no metric labels, raw values, host/IP names, query logs, secrets or exported raw sample arrays. Output intervals are capped at 128 items of each class; exceeding caps fails closed to UNKNOWN.
- tests/test_v06_coverage_model.py: synthetic-only positive and negative tests for no-gap coverage, >10-hour missing data, leading/trailing gaps, invalid samples, timestamp mismatch and small allowed skew, 4963-row 7d input, invalid shapes/labels/values and response bounds. CI and Fedora operator-run offline acceptance must be checked independently on the final PR SHA.
