## Result and boundary

J performs **one real HTTP exchange with its own temporary synthetic peer**.
The peer binds numeric IPv4 `127.0.0.1` and an OS-selected unused port, checks a
per-instance capability and the exact selected [I](V0.14.5I-OFFLINE-BATCH-PLAN-LAB.md)
request body, and returns a scripted response. A bounded Python worker sends
one [H](V0.14.5H-OFFLINE-LOKI-REQUEST-LAB.md) JSON body. No URL/host/port option,
proxy routing, redirect following, retry, actual Loki endpoint or file input.

This is a controlled HTTP fixture result, **not a real Loki receipt**, durable
receiver, server acceptance/readback or F/G ACK protocol. The peer retains one
body in volatile memory only. No ACK/checkpoint, source or receiver file is
changed. After the successful lab exchange, all 33 planned records remain
pending and the two declared synthetic ACKs remain unchanged.

  and [subprocess](https://docs.python.org/3.12/library/subprocess.html#subprocess.Popen.communicate)
  documentation: socket operation timeouts and a whole-child timeout are
  different bounds; timeout cleanup requires killing and reaping the child.

No installed Loki build/config, TLS, tenant/authentication, blocked-ingestion
configuration, server time window or real ingestion was tested.

## Exchange and budgets

| Element | Implemented scope |
| --- | --- |
| Plan | Full I recomputation against provided source/ACK bytes before worker start |
| Destination | Active, matching, owned `127.0.0.1:0` fixture; actual address read from its listener socket |
| Request | One selected H body, at most 16 records / 64 KiB, fixed POST path/content type |
| Private worker job | Bounded 128 KiB ASCII JSON/base64 frame, exact schema/body checksum; no host/URL field |
| Socket timeout | 2 seconds per worker blocking operation |
| Parent child deadline | 2 seconds for communication/exchange after process creation |
| Timeout/interrupt cleanup | Kill client and communicate/reap with a separate 1-second cleanup bound |
| Response | Application reads at most 513 bytes, rejects above 512; compact report at most 1 KiB |
| Header checks | At most 16 fields / 4 KiB after standard-library parsing; no transfer encoding or duplicate length |
| Attempts | One worker and one attempt per fixture, including failed/uncertain attempts |
| Peer cleanup | Release stall gate, shut down active connection, close listener, stop server thread |

The process-creation call itself is not covered by `communicate` timeout.
Header checks happen **after** `http.client` parsing, not through a custom
preallocation-limited parser. Worker code/imports and fixture code are trusted;
this is not a subprocess sandbox or a production hostile-peer HTTP audit.
OS-level process/thread scheduling or uninterruptible cleanup is not a
hard-real-time guarantee. Cleanup failure causes HOLD, never a success marker.

## Validation before a positive fixture result

1. I rejects stale/altered plan inputs, types, body or membership before client
   creation. Invalid index, empty plan, foreign/unopened/closed/mismatched peer
   holds without a send. A fixture cannot be reopened or automatically retried.
2. The parent obtains the address from its owned listener, not a user URL, and
   supplies the private capability/body/checksum to one fixed-host worker.
   `http.client` does not use proxy environment variables or follow redirects
   in this code. Server bind avoids `getfqdn`/reverse host lookup.
3. The peer checks route, content type, capability, bounded content length and
   exact bytes, then records one synthetic body. It emits no request/body log.
4. The worker reads a bounded response and reports only status, body length and
   framing checks. Strict types reject boolean/numeric equality coercions.
   Only exact `{status:204, body_bytes:0, framing:true}` is a candidate result.
5. The parent additionally requires the controlled peer's empty normal-204
   script, one observed POST and exact request bytes. A fabricated successful
   worker report without a request cannot pass. A scripted extra body with
   misleading zero length cannot pass merely because the HTTP parser treats
   204 as bodyless. This joint check depends on owning the peer and does not
   generalize to an opaque Loki server.
6. The client is reaped, context cleanup closes the listener/thread, and the
   unchanged I plan still validates. Return value is a fixture marker, not an
   ACK dictionary; it is not connected to F/G advancement or durable storage.

| Scenario | Observation required by tests |
| --- | --- |
| Normal owned 204/empty reply | Exact one request, client reaped, peer closed, no progress change |
| 200 / blocked-style 260 / redirect / 429 / 500 | HOLD; no redirect or automatic retry |
| Extra body, duplicate length, transfer encoding | HOLD, including misleading zero length on a scripted extra body |
| Disconnect / malformed status | HOLD, attempt consumed |
| Stalled real peer | Parent deadline terminates/reaps client; peer closes |
| Injected `KeyboardInterrupt` / communication `OSError` | Client killed/reaped, original exception preserved |
| Reap timeout | HOLD; no claim of successful cleanup |
| Wrong capability/body, stale plan or peer mismatch | No positive fixture result; wrong source/plan stops before client start |

## Reproduce and validation

From the HCC experiment directory, Linux/Python 3.10+ and permission to bind an
ephemeral IPv4 loopback socket and start one Python child:

```bash
python3 -B tools/v0145j_loopback_exchange.py --self-test
python3 -B -m unittest discover -s tests -p 'test_v0145j*.py' -v
python3 -B tools/v0145j_loopback_exchange.py --lab
```

Self-test uses memory only and denies file/socket/process creation. **Lab and
network unit cases use their own loopback listeners and bounded children**;
their `NETWORK` marker intentionally differs from A–I. No root, actual service
port, production path, journal input or real endpoint is accepted. No data
files are written; the worker uses `python -B`. CLI prints only counts/markers,
not capabilities, scope, IDs, bodies or error response content.
