**Status:** operator-reported Fedora-only acceptance of V0.13.2a; V0.14 is a **source-only Draft PR plus operator-accepted isolated Fedora labs through V0.14.4b**; V0.14.5 remains a proposal. `DEPLOYMENT_GATE=HOLD`. No router contact, production changes, permanent HCC service, journal permission changes, Alloy reload, Loki ingestion or automatic incident classification.

## Problem and evidence boundary

An absent DNS Guard metric sample means **missing sampled telemetry**, not necessarily router downtime, WAN failure, a DNS outage or DNS Guard failover. The existing seven-series V0.6 B1/B2 local VictoriaMetrics adapter is manual and strictly bounded; observed sample parity does not establish continuously healthy service or full history completeness.

V0.13 classified 21 sampled telemetry gaps from 4,963 seven-series rows (one invalid sample) in a seven-day period. V0.13.1 correlated those gaps with 33 paired Fedora kernel suspend/resume events; five gaps had at least 90% suspend overlap, two had partial suspend overlap, fourteen had no paired-suspend overlap. Missing paired-suspend records are **not** proof that Fedora remained awake. This standalone stage did **not** analyze boots.

V0.13.2 initially rejected a legitimate `journalctl --list-boots` column header. V0.13.2a accepts the recognized `IDX BOOT ID FIRST ENTRY LAST ENTRY` header at the start only, while retaining strict validation of entries and DST-aware Europe/Warsaw timestamps. Synthetic self-tests: 31/31 PASS. In the operator-run seven-day correlation: 21 gaps, 33 suspend pairs, 81 boot records, 13 interboot intervals and 82 distinct collector `exit 255` events within the query window.

| V0.13.2a label | Gaps | Evidence meaning |
| --- | ---: | --- |
| `FEDORA_INTERBOOT_BOUNDARY_CORRELATED` | 8 | overlaps intervals between last and first *journal records* of consecutive boots |
| `FEDORA_SUSPEND_CORRELATED` | 5 | >=90% overlap with paired suspend/resume records |
| `PARTIAL_FEDORA_HOST_CORRELATION` | 3 | partial suspend or interboot correlation |
| `MIXED_HOST_AND_COLLECTOR_EVIDENCE` | 1 | both host-event overlap and failed collector execution |
| `COLLECTOR_EXIT_255_OBSERVED` | 4 | collector process exits, no host-event overlap |
| `UNKNOWN_NO_MATCHING_EVIDENCE` | 0 | no gap entirely unmatched by the selected sources |

The categories identify **matching evidence**, not definitive causes. Interboot record edges are not exact shutdown/power transition timestamps. Unmatched parts of each interval remain unexplained, even when a gap has a dominant host-event classification. Journal completeness has not been established; one invalid metric row prevents complete sample validation. No numerical ratio should be described as DNS uptime or host uptime.

### Two representative historical collector gaps

28 Oct 2026, local Warsaw time:

- Gap #17 (16:07:19–16:52:45) overlaps kernel suspend entry 16:08:11 and resume 16:51:32 for approximately 95.4% of its duration. A single failed collector attempt with exit 255 followed resume. This supports `FEDORA_SUSPEND_CORRELATED`; the residual interval does not become a DNS outage.
- Gap #18 (17:04:26–17:25:04) contains 18 distinct collector exits with status 255. Gap #19 (17:31:35–18:12:47) contains 37; 55 combined. Related journal text included timeout signals, but whether the underlying fault was SSH, router management access, Ethernet or WAN remains unresolved. Do not equate three systemd messages about one exit with three failed runs.

A later Oct 29 WAN-speed event (sampled 100 Mbps at 18:51 and 18:51:30, back to 1000 Mbps at 18:56:27) was independently observed alongside some probe failures. It is **not** proof that the Oct 28 collector gaps were caused by WAN.

## V0.14 proposed design (NOT DEPLOYED)

Maintain the existing systemd user timer `dns-guard-monitoring.timer`, its SSH collection and direct metrics import to local VictoriaMetrics. Do not replace or modify it merely to add observability.

Optional laboratory path:

```text
explicit, bounded journalctl --user -u dns-guard-monitoring.service -o json
     -> local strict sanitizer (no raw text emitted)
     -> low-cardinality JSONL event stream (explicit manual-only output)
     -> APPROVAL GATE: private file spool and permissions
     -> Alloy loki.source.file (proposed config fragment)
     -> existing loki.write.local -> Loki
```

Alloy currently tails a Pi-hole NDJSON activity file; it does not transport DNS Guard metrics. Reading the *system* journal via `loki.source.journal` is not equivalent to reading a specific user's systemd unit journal. Do not grant broad `adm`/`systemd-journal` access, expose raw SSH error messages or restart Alloy as an unreviewed workaround. See official [Alloy file source](https://grafana.com/docs/alloy/latest/reference/components/loki/loki.source.file/) and [processing stages](https://grafana.com/docs/alloy/latest/reference/components/loki/loki.process/).

The lab sanitizer is designed to output only event time, a fixed component name, a fixed source name and a fixed event class (collector exit 255, SSH timeout, SSH authentication failure, HTTP import timeout). No hostnames, addresses, session details, tokens, raw stderr, client names or DNS queries belong in the output. Matching a coded error still does not prove the root cause. The standalone Polish manual HCC view displays only the validated V0.13.2a report and operates offline without JavaScript, backend endpoints or new UI privileges.

**Original design gates (before the October 29 acceptance below):** owner-approved dataflow; verify journal-unit provenance; choose private spool path and rotating writer; safe group permissions for Alloy; prevent raw event leakage; run actual installed Alloy syntax validation; test synthetic Loki ingestion, label cardinality and retention; operational rollback; explicit review of source-versus-running config and Grafana alert routing. None of these has been accepted for production.

### Local artifacts and scope

The V0.14 offline lab bundle is deliberately separate from the production config and contains a Python sanitizer, a static HTML renderer, a *non-applied* Alloy configuration fragment and synthetic/negative tests. Self-tests do not perform network requests, contact ASUS or write files. Rendering a report requires an explicit destination filename and refuses overwrite; outputs must not be published to the public repository without sanitization review.

**Do not merge or deploy based on this document alone.** The source-only draft PR records bounded findings and design; it is not a claim of production integration.

### Important implementation caveats

- `V0144_RESULT=PASS_MAC_DAC_SYNTHETIC_ONLY` is acceptance of **one isolated, disposable process with matching Unix identity and SELinux label**, *not* acceptance of the production Alloy unit, the real spool path, journal-to-file writer, ACL on restart, SELinux label persistence, live Loki delivery, or ongoing privacy controls.
- The original `HOLD_WRONG_SELINUX_CONTEXT` must remain recorded. V0.14.4a identified `context="system_u:system_r:unconfined_service_t:s0\\u0000"` before normalization; the fixed probe accepted `context="system_u:system_r:unconfined_service_t:s0"`. Extra/embedded NUL, wrong UID, wrong context, unexpected write or `nobody` read continue to reject. This was a **parser/contract correction**, not a change to SELinux policy.
- The proposed `/var/lib/hcc-dns-guard/collector-events.ndjson` **was not created**. No long-running writer or retention process exists; the real journal has no automatic new Loki tail. The original `monitoring/alloy/config.alloy` remains unchanged by this HCC work.
- The workstation's actual Alloy process was observed in supplementary `adm` and `systemd-journal` groups; these may allow broad journal access subject to filesystem permissions and SELinux. Do not present Alloy as unprivileged beyond these facts, remove existing groups, or recommend blindly tailing the user's raw journal.
- No production DNS/WAN fault attribution, router contact, new HCC autostart/HTTP endpoint, alert routing, Grafana rule change, production spool, or live Loki ingestion was established by these labs.

### V0.14.5 — next-session design, not yet implemented

1. Design a **trusted, unit-scoped, bounded journal reader** with source provenance, sanitized-only output and explicit error states. Distinguish a collector run from multiple journal messages about the same run; do not send raw SSH stderr, hostnames, addresses, tokens or DNS query payloads to Loki.
2. Define an **atomic private spool writer** (permissions before publish, no symlink traversal, exclusive/temporary writes, bounded backlog, crash-recovery and duplicate handling) with dedicated allowlisted low-cardinality labels. Preserve timestamps and clock-uncertainty limitations.
3. Specify rotation/retention and restart behavior with explicit ownership/ACLs, verified `var_lib_t` labeling and non-world-accessible parent directory. Check on the actual runtime path and after reboot; a `/tmp` or transient `/var/lib` PASS alone does not validate this.
4. First test a separate, synthetic-only writer → spool → Alloy → fake Loki receiver flow. Require negative tests, bounded resource use, cleanup/rollback and evidence for full read/deny matrix before requesting any persistent setup.
5. Require an **explicit separate deployment decision** before modifying active Alloy config, creating a durable `/var/lib/hcc-dns-guard` path, adding a service/timer, or connecting events to Grafana/HCC.
