## Result and boundaries

[E](V0.14.5E-ATOMIC-HANDOFF-LAB.md) retains IDs with complete payloads, but does
not know which records a receiver acknowledged. F adds a **volatile in-process
fake receiver** and a private per-record ACK file in a separate disposable
directory. One call attempts at most one unacknowledged E record. No source
payload is deleted, including acknowledged payloads.

This models receive → exact ACK → saved ACK state. It is not an actual Loki
HTTP acknowledgement protocol, durable remote receiver, autonomous retry loop
or exactly-once guarantee. Fake-receiver ACKs attest only that trusted test code
accepted the provided bytes in memory. Receiver durability is not implemented.

## Protocol and state

| Element | Contract |
| --- | --- |
| Source | Completely validated E `handoff.json`, retaining all records |
| Receiver | Trusted in-process callback, shipped fake uses memory only |
| Fake ACK | Exact schema `hcc-v0145f-fake-receiver-ack/1`, scope, event ID and SHA-256 of exact canonical event bytes without newline |
| State | `delivery-acks.json`: owned 0600 regular single-link file, separate owned 0700 directory |
| State schema | `hcc-v0145f-ack-store/1`, scope, sorted unique ID/payload-hash pairs and corruption digest |
| Limits | 1,024 ACK pairs / 256 KiB; E retains its independent bounds |
| Ordering | E's lexicographic ID order, not chronological delivery |
| Lock | A's nonblocking cooperative directory lock on both directory descriptions |

Keep source and ACK directories separate. Both locks remain held through the
receiver call; do not share one open file description between concurrent
callers. Ancestors must be trusted; root and uncooperative same-UID mutation
are outside scope. Python callbacks are trusted code, not a sandbox or a real
transport with deadlines/backoff. The CLI accepts no paths, URLs, keys, input
files or receiver configuration.

## Dispatch steps

1. Validate source/ACK directory owner and mode, and require distinct directory
   inodes. Read/verify the entire E snapshot. Missing/corrupt source causes HOLD
   without creating ACK state or attempting a receive.
2. Read complete ACK state with no-follow/nonblocking final-file open, bounded
   reads, before/after metadata, strict schema/count/byte/order/digest/canonical
   validation. Unknown entries and orphan `.ack-<32hex>.tmp` names HOLD without
   deletion. Corruption never implicitly resets to zero.
3. Check scope and every saved ACK against the retained source ID and exact
   payload hash. A missing/changed acknowledged source record or key scope is
   HOLD, even if the source file itself has a newly valid unkeyed digest.
4. In an otherwise empty state directory, atomically initialize an empty ACK
   set before the first receive. Retry source/state directory sync barriers.
   Select the first unacknowledged ID; completion sends nothing.
5. Call the fake receiver once. Require an exact string-valued schema/scope/ID/
   payload-hash ACK. Wrong/extra/missing fields or receiver error never advances
   the ACK set. The fake receiver does not deduplicate attempts.
6. Add exactly that one pair and atomically replace the private ACK file:
   exclusive temp, enforce 0600, complete write, file fsync, replace, directory
   fsync, then successful return. Compare expected prior state; no initialization
   with ACKs, rewind, hash overwrite or jump of multiple new ACKs is allowed.
7. No E records are removed. E may append new records under the same scope;
   saved ACKs remain a validated subset. A newly appended lower ID is not
   skipped because F tracks IDs rather than a last-ID watermark.

Both source and ACK files use unkeyed corruption digests. Valid-looking state
can be forged by a trusted caller/same-UID writer; these digests do **not**
authenticate a receiver or journal source. The internal state writer's monotonic
guard is not proof that an arbitrary caller actually obtained ACK. D's public
fixture key is not a host-key lifecycle or source-provenance design.

## Failure observations

| Scenario | Test expectation |
| --- | --- |
| Wrong fake ACK or receiver exception | Initialized ACK set stays unchanged; E data retained |
| Verified receiver ACK, then interruption before store | Same source record attempted again on retry |
| ACK-file fsync before replace, ordinary exception | Old ACK file remains; own temp cleaned |
| Abrupt child exit after ACK-file fsync | Orphan temp HOLD on reopen; E records retained |
| Error/exit after ACK replace, before directory sync | New valid ACK may be visible; not a successful durability return |
| Error/exit after directory sync, before return | Saved ACK prevents that ID being attempted again; other IDs remain pending |
| File sync / replace / zero write | No success return, old ACK state retained |
| Directory barrier before receive fails | No receive attempt |
| Source record previously ACKed disappears/changes | HOLD before another receive |
| Explicit deletion of all ACK state in a negative fixture | Replays from the start; source still retains payload |
| Append after completion, including a lower ID | New record attempted and ACKed without rewriting prior ACKs |

Actual five-second-bounded child tests use `os._exit` at four phases: after
verified receiver ACK/before store, ACK temp fsync, replacement, and final
directory sync before return. Child output records the synthetic attempted ID.
These are process-exit tests, not power-loss or remote-receiver durability tests.
The fake receiver's memory can disappear with a process; saved ACKs therefore
must not be described as proof of delivery to a durable receiver. E retains
all source bytes regardless. There is no atomic transaction across the source,
ACK store and an external receiver.

## Reproduce and validation

From the HCC experiment directory, Linux/Python 3.10+:

```bash
python3 -B tools/v0145f_delivery_ack.py --self-test
python3 -B -m unittest discover -s tests -p 'test_v0145f*.py' -v
python3 -B tools/v0145f_delivery_ack.py --lab
```

F: **37 tests**. At the F checkpoint, A–F had **189** focused cases, full HCC
Python **394** and JavaScript **55**. Run outcomes and CI references are in the
[worklog](../../../docs/worklog/2026-10-30.md). Self-test uses memory only;
lab/unit files stay in freshly created `/tmp` trees and are removed on exit.
Both CLI modes preserve `DEPLOYMENT_GATE=HOLD`. Expected lab marker:
`V0145F_RESULT=PASS_DISPOSABLE_DELIVERY_ACK_ONLY`, with
`ACK_PROTOCOL=IN_PROCESS_FIXTURE_NOT_LOKI`, `RECEIVER_DURABILITY=NOT_IMPLEMENTED`,
`POWER_LOSS_DURABILITY=NOT_TESTED`, retained source count 3 and four receive

was updated together. No F Fedora operator result exists at this checkpoint.

Later [G](V0.14.5G-DISPOSABLE-FILE-RECEIVER-LAB.md) adds a separate disposable

snapshot remains available. F itself retains its original volatile receiver;
G does not establish real transport, exactly-once or power-loss durability.

## Remaining gates

Actual durable receiver/transport ACK semantics and time bounds, source
authentication and host-key lifecycle, A–C/Alloy schema integration, persistent
production ownership/SELinux/ACL, delivery-coordinated retention, recovery after
physical power loss and operational rollback. ACK-file loss can cause replay;
external/forged ACK state can cause false acknowledgement. These limits are not
solved by the synthetic model. No automated scheduler or GC exists.

**No real journal, real receiver/Loki/Alloy, network, ASUS, HCC HTTP/UI, systemd,
service configuration, event deletion, merge or production deployment.
DEPLOYMENT_GATE=HOLD.**
