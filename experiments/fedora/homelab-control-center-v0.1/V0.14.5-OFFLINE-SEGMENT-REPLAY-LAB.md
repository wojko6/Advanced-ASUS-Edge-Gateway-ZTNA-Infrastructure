### V0.14.5A publication contract and corrections

- Input is the **shape** of V0.14 sanitizer output, not authenticated provenance:
  only `time`, `kind`, `component=dns-guard-collector` and
  `source=fedora-user-journal`. Four classes are allowed: `COLLECTOR_EXIT_255`,
  `SSH_TIMEOUT`, `SSH_AUTH_FAILURE`, `HTTP_IMPORT_TIMEOUT`. UTC timestamps have
  exactly millisecond precision and years 2000–2100. Duplicate JSON keys,
  unknown fields, non-string values, duplicate canonical rows and decreasing
  timestamps are rejected. A batch is at most 256 rows and 32 KiB, both raw and
  canonical; the byte limit can be reached before 256 rows.
- Owned `0700` directory, owned regular `0600` segment, one hardlink, canonical
  bytes and matching SHA-256 filename are mandatory. Exact file mode is set
  before publication even with a restrictive inherited umask. `O_NOFOLLOW` protects the
  **last** directory component and descriptor-relative segment operations;
  ancestors must already be trusted. Same-UID hostile processes and root are
  outside this cooperative laboratory boundary.
- A nonblocking Linux `flock` on the directory open-file description excludes
  independently opened cooperating writers/readers. Closing the descriptor
  releases it. Do not share one description between concurrent threads or
  processes; this is not a multiwriter scheduler or a security boundary against
  an uncooperative same-UID writer. Directory mode/owner are rechecked by public
  operations, including callers that supply a descriptor directly.
- Enumeration stops after the 128-entry limit. Before creating a new file or
  accepting an exact duplicate batch, **every existing segment is verified**.
  The original 19-test baseline incorrectly accepted a new batch when a
  different existing segment was corrupt; this was reproduced before correction
  (`BASELINE_UNRELATED_CORRUPTION=PUBLISHED_ATOMIC_SEGMENT`). Regression cases
  now reject that state without creating a file.
- Reads use `O_NONBLOCK` before checking regular-file metadata so a named FIFO
  cannot hang `open()`. Short reads/writes are handled; metadata is compared
  before and after reading. This is not a claim of resistance to every concurrent
  malicious filesystem change.
- Publication is exclusive `.tmp-*` creation, complete write, file `fsync`,
  hardlink-if-absent to `segment-<sha256>.ndjson`, unlink temporary name, directory
  `fsync`. Exact batch replay verifies the entire backlog and retries directory
  `fsync`; it writes no new segment bytes. An I/O error never returns success.
  Directory-sync failure may leave a visible final segment without a successful
  durability acknowledgement.
- Unexpected entries and orphan temporary names cause HOLD, with no automatic
  repair or deletion. Real child processes using `os._exit` after file sync or
  after link publication left the expected residue; the next opener acquired
  the released lock and refused publication. **Process exit is not power loss**;
  filesystem crash durability and recovery after reboot remain untested.
- Retention remains a candidate preview based on event time, **not delivery
  acknowledgement**, trusted wall clock or permission to delete. Clock changes,
  overlapping batches and the reader lifecycle prevent treating it as safe GC.

### V0.14.5B snapshot and acknowledgement contract

1. Verify the entire bounded backlog, copy its canonical bytes into memory and
   freeze a manifest ordered by `(first event time, last event time, filename)`.
   At most 128 segments × 32 KiB = 4 MiB of segment payload; parsing and object
   overhead are additional. The manifest fingerprint binds the ordered segment
   names, which themselves bind content hashes.
2. Refuse an identical canonical row across different batches with
   `AMBIGUOUS_CROSS_BATCH_EVENT`. Do **not** silently discard it: two real events
   can share the millisecond timestamp and class because the sanitizer drops
   boot/cursor identity and microseconds. Also refuse interleaved segment time
   ranges until an ordered merge contract exists. Equal times with different
   classes can be retained.
3. Restore only a ≤256-byte JSON checkpoint with exact schema, snapshot digest
   and integer acknowledged-prefix count. Extra/duplicate keys, boolean counts,
   invalid bounds or a different snapshot cause HOLD. This is an integrity/shape
   check, **not authentication of a checkpoint or journal event**.
4. Send at most one frozen segment to the shipped **in-memory fake receiver**.
   Only an exact filename ACK allows returning a checkpoint advanced by one.
   A receiver exception or wrong ACK does not advance it. Completion sends
   nothing but still verifies the full backlog.
5. Rebuild and verify the snapshot on each call. Adding/removing a segment or
   corrupting any segment cannot silently reuse an old checkpoint. This contract
   intentionally freezes one backlog; it does **not** support continuously
   extending a live stream or rebasing a cursor after GC.
6. A test interrupts after receiver ACK and before checkpoint return. Retrying
   with the previous checkpoint produces a **duplicate receive attempt**. The
   lab explicitly models at-least-once attempts under retry, not exactly-once
   delivery, durable persistence or Loki acceptance. No automatic retry loop or
   checkpoint file is installed, and no segment is deleted.

## Explicitly not accepted / next stages

- No actual Fedora workstation test in this session, no SELinux/DAC matrix on
  the workstation at the **initial Work-only checkpoint**. The later operator
  A/B lab acceptance above supersedes only the no-Fedora-lab statement. No
  SELinux/DAC matrix, ACL/label persistence or cold reboot was tested. Alloy
  and SELinux tooling are absent in the Work container.
- No trusted journal reader, journal cursor, stable event identity, proof of
  unit provenance or microsecond-preserving schema. Real input must not be
  connected to this shape-only interface as if these gates were satisfied.
- A–B has no checkpoint file; C adds a separate disposable-file transaction.
  No production checkpoint durability, event-level deduplication, safe retention
  deletion, post-power-loss recovery or delivery guarantee. A valid-looking
  checkpoint supplied by untrusted code could falsely claim acknowledgement.
- No actual Alloy process/config validation or fake Loki HTTP E2E here. The
  existing unapplied [V0.14 Alloy fragment](monitoring/v014-dns-guard-sanitized.alloy.fragment)
  tails one file, and **does not implement this immutable-snapshot contract**.
  V0.14.5B is an independent offline model, not an Alloy adapter or Loki ACK API.
- No real journal, ASUS, production Loki/metrics, active HCC endpoint, service,
  timer, firewall, Grafana rule or running Alloy config was contacted/changed.
