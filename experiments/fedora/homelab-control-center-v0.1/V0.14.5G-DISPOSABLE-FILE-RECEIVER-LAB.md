## Result and limits

[F](V0.14.5F-SYNTHETIC-DELIVERY-ACK-LAB.md) deliberately uses a volatile fake
receiver. G adds a separate **disposable file-backed synthetic receiver**,
which stores the complete event before returning the same in-process fixture
ACK. If the receiver stored an event but the caller lost its ACK/progress,
retry finds the retained ID and identical bytes without rewriting the receiver
snapshot. Reopen and independent-process tests exercise this behavior.

This is idempotent storage within one retained synthetic receiver snapshot.
It does not establish exactly-once external effects, actual Loki ingestion,
remote-receiver durability, physical power-loss recovery or an installed queue.
All source and receiver payloads remain retained; no GC or automatic retry exists.

## Three separate stores

| Directory role | File / contract | Bound |
| --- | --- | --- |
| Source | E `handoff.json`, full retained D-format events | 1,024 events / 512 KiB |
| Sender ACK state | F `delivery-acks.json`, scope plus ID/payload-hash pairs | 1,024 pairs / 256 KiB |
| Synthetic receiver | Separate E-format `handoff.json`, full retained received events | 1,024 events / 512 KiB |

G reuses E's schema, complete snapshot decoder/reader, metadata checks and
orphan rules. No new persistence schema or real transport adapter is introduced.
An individual receiver call additionally bounds payload to **4,096 bytes** and
requires exact canonical bytes, declared scope and event ID. It does not
reconstruct source envelopes or read a key. The public D fixture key remains
synthetic; unkeyed file digests detect corruption, not authentication.

The three directory inodes must be distinct. Each directory is owned 0700,
each file owned 0600, regular and single-link. A's nonblocking cooperative
directory lock remains held through validation, receive and ACK storage until
the caller closes each description. Do not share descriptions between
concurrent callers. Ancestors/callers must be trusted; root, uncooperative
same-UID mutation, role forgery and authenticated rollback detection are outside
scope. Identical E schemas do not authenticate source versus receiver roles.

## Dispatch and acknowledgement

1. Validate failpoint selectors and lock/check all three distinct directories.
2. Require/verify the whole E source and read the complete F ACK and receiver
   states. Corrupt, unsafe, unknown or orphan state holds before initialization
   or another receive; no implicit reset/deletion.
3. Require matching scope. Every receiver record must still have identical
   source bytes. Every saved ACK must have an identical receiver payload hash.
   The retained relationship is **ACK ⊆ receiver ⊆ source**, including full
   content consistency. Validate it even when all ACKs appear complete.
4. Use F's dispatcher for at most one pending source ID. Its callback validates
   the individual record and the entire receiver snapshot. Same ID/different
   bytes, scope/capacity or schema conflicts hold without partial merge.
5. For a new receiver ID: validate complete prospective snapshot, exclusive
   private temp, complete write, file fsync, atomic replace, directory fsync,
   then return the exact F fixture ACK. On a duplicate, retry directory fsync
   and return ACK without rewriting the already synced payload file.
6. F verifies the exact ACK before its separate atomic ACK-file advancement.
   There is no cross-file or distributed atomic transaction. Lost ACK/state
   can repeat a receive attempt, but retained receiver IDs avoid duplicate
   snapshot insertion. New lower IDs after completion remain eligible through
   F's set-based progress; ordering is lexicographic ID, not chronological.

The ACK schema remains `hcc-v0145f-fake-receiver-ack/1`; it is **not** Loki's
HTTP protocol. File acceptance is not proof of journal provenance or real
service ingestion, and no external effects are modeled.

## Failure observations

Actual child tests use `os._exit(23)` with a five-second bound per child. Parent
reopens distinct descriptors; all E source payloads remain available.

| Exit / failure | Visible model state | Retry result |
| --- | --- | --- |
| Receiver temp-file fsync, before replace | Receiver orphan, ACK unchanged | HOLD, no automatic cleanup |
| Receiver replace, before directory fsync | Complete receiver event may be visible, no ACK advance | Same-ID receive retries directory barrier without insertion |
| Receiver directory fsync, before callback ACK | Receiver event, ACK unchanged | Same retained ID, no snapshot rewrite |
| Verified fixture ACK, before sender store | Receiver event, empty prior ACK state | Same retained ID, then one saved ACK |
| ACK temp-file fsync, before replace | Receiver event, ACK orphan | HOLD, source and receiver retained |
| ACK replace, before directory fsync | Receiver event and new ACK may be visible | Next pending ID; no success/durability return from terminated child |
| Receiver file/write/replace/sync error | No ACK advancement; old state or complete replaced state | Validate whole state before retry |
| Missing/changed receiver record with saved ACK | Inconsistent stores, even after apparent completion | HOLD before receive |
| Explicit ACK-file deletion in negative fixture | Receiver still retains all records | Replay without receiver rewrite |
| Explicit receiver + ACK-file deletion | No independent monotonic anchor | Loss is indistinguishable from new state; rebuild/replay observed |

These are process-exit and injected I/O observations on disposable storage,
not disk power-loss tests. No cold reboot, journal recovery, real transport,
SELinux/ACL persistence or receiver failover was tested. Losing/rolling back
both state files can defeat the retained-ID model. Forged valid source/receiver/
ACK files can satisfy its consistency checks; they are not authenticated.
