## Problem and boundary

The V0.14 sanitizer drops the raw source record identity and reduces time to
milliseconds. Distinct records can therefore have equal time/kind after
sanitization. The [A–B model](V0.14.5-OFFLINE-SEGMENT-REPLAY-LAB.md) correctly
refuses that ambiguity; [C checkpoint files](V0.14.5C-DISPOSABLE-CHECKPOINT-LAB.md)
do not fix it. Identical event class/time is not a safe journal event ID.

D models a **new synthetic source-envelope schema** that retains record identity
without copying boot/cursor into output. It is not a real journal reader or a
claim that a field with the right unit name proves source provenance. It does
not modify A–C, the V0.14 sanitizer, HCC HTTP/UI or any monitoring service.

## Synthetic envelope and new event schema

Input contains exactly five string fields: `boot`, `cursor`, `time_us`, `unit`
and `kind`. The pure Python interface accepts a bounded byte batch and a
32-byte test key. The CLI exposes only `--self-test` and `--lab`, both synthetic
memory-only; no stdin, filename, URL, real key or journal option exists.

| Field | Contract | What it does not establish |
| --- | --- | --- |
| `boot` | 32 lowercase hex characters | An observed boot or actual machine identity |
| `cursor` | 1–512 ASCII token characters from a narrow allowlist | A valid systemd cursor, record existence or trusted origin |
| `time_us` | Canonical 15–16-digit positive ASCII decimal, years 2000–2100 | Truth of the source clock or complete capture |
| `unit` | Exactly `dns-guard-monitoring.service` | Authenticated unit attribution |
| `kind` | One of the four existing fixed classes | Root cause, collector-run identity or independent incident count |

Reject duplicate/extra/missing keys, non-string/nonfinite values, unknown classes,
wrong unit, invalid boot/cursor, out-of-range times, blank lines and decreasing
times **within** a batch. Limit **128 rows / 64 KiB** input and canonical output
independently. The row/byte limits can constrain each other. Cross-batch wall
clock order is not enforced by this identity model.

The new output has exactly seven fields: `schema`, `scope`, `event_id`, `time`,
`kind`, `component`, `source`. Schema is `hcc-v0145d-identity-event/1`, component
is fixed `dns-guard-collector`, source is explicitly **`synthetic-unit-envelope`**.
Time uses six UTC fractional digits, converting integer microseconds directly
with `timedelta`; no floating-point timestamp conversion.

`event_id` is HMAC-SHA256 of canonical domain-separated JSON containing the
synthetic boot, cursor and fixed unit. Time/kind are **not** part of identity:
a changed payload under the same record identity must be detected as conflict,
not quietly assigned a new ID. `scope` is a different domain-separated HMAC
under the same key; a key change after ledger initialization causes HOLD.
JSON encoding/key order does not affect canonical identity.

Raw boot, cursor, unit input and key are not copied into event output. Stable
IDs still allow correlation, and timestamps/classes are intentionally retained.
This is a **pseudonymization model, not anonymity or source authentication**.
The shipped deterministic fixture key is public and must never protect real
input. There is no entropy check, host-key creation/storage, rotation, migration,
source authority or independent key ownership. HMAC values made with a key known
to the caller do not authenticate a journal source. Do not publish/transport real
envelopes through the fixture CLI or treat its model as a production key design.

## Bounded ledger behavior

- First completely accepted batch binds the key scope. A rejected first batch
  does not leave a partially initialized scope or entries.
- Track up to **1,024 identities** in a cooperative, single-caller in-memory
  ledger. Only canonical **sanitized output** is retained, not raw envelopes or
  the caller's key. At 64 KiB/128-row batch bounds this is finite, but Python
  object overhead is additional; no exact heap-byte guarantee is claimed.
- Identical ID and identical canonical payload is a replay: emit no new event
  for that envelope. Repeated envelopes within the same batch behave likewise.
  Different IDs with equal time/kind are preserved as separate source records.
- Same ID with changed canonical time or kind causes
  `SAME_ID_DIFFERENT_PAYLOAD`. Validate the entire batch before changing the
  ledger: a valid new prefix followed by conflict cannot partially commit.
- Capacity refusal never evicts old entries or partially commits a new batch.
  Known exact replays can still be recognized at capacity. Scope changes cause
  HOLD rather than silently re-ingesting under a new key.
- Ledger loss/restart reaccepts old records. There is **no persistent dedup state,
  delivery ACK, shared multiwriter synchronization or exactly-once guarantee**.
  This source-record model does not deduplicate the C fake receiver's delivery
  attempts and does not identify a service execution or incident.

Ledger acceptance is not downstream delivery: discarding a returned batch after
a later sink/spool failure would leave its IDs seen in that same volatile
ledger, so another accept emits no new bytes. A future integration must design
an explicit durable handoff/commit transaction before using these semantics in
a live producer. D does not claim lossless delivery or provide that transaction.

The later [E disposable handoff model](V0.14.5E-ATOMIC-HANDOFF-LAB.md) uses this
module's normalization without precommitting its volatile ledger, publishing
IDs and complete payload together. D itself remains memory-only, and E is not
a real source/receiver, A–C migration or installed production transaction.

## Explicit incompatibility with A–C

The new fields, microsecond time and synthetic source do **not** match A–C's
four-field millisecond schema. A regression test requires the old spool to
reject D output. No adapter silently strips identity to make it fit. D is a
separate contract exercise, not an integrated journal → spool → Alloy pipeline.
IDs/scopes would need to remain record fields, not high-cardinality Loki labels,
in any separately reviewed future transport design.

## Reproduce and validation

From the HCC experiment directory, Linux/Python 3.10+:

```bash
python3 -B tools/v0145d_event_identity.py --self-test
python3 -B -m unittest discover -s tests -p 'test_v0145d*.py' -v
python3 -B tools/v0145d_event_identity.py --lab
```

Work observations: **31/31 D tests PASS**, CLI self-test and lab PASS. Tests
include independently constructed HMAC wire-message expectations, microsecond
and UTC bounds, strict envelope/privacy/schema boundaries, overlapping batches,
same-ID conflicts and atomic refusal, key-scope changes, capacity and ledger
loss. A mocked I/O guard checks that both CLI functions use no files, sockets
or subprocesses. Full HCC regression: **323 Python / 55 JavaScript PASS**.
A–D now contains **118** focused cases; only the earlier A–B 59 and C 28 have
operator Fedora results, in separate runs. D has **no Fedora acceptance** yet.

The 323/118 totals above are the D checkpoint. E later adds 34 cases, and
[F's disposable ACK model](V0.14.5F-SYNTHETIC-DELIVERY-ACK-LAB.md) adds 37:
at the F checkpoint full HCC Python **394**, A–F **189**, JavaScript **55**. D still has 31
cases. F uses a volatile fake receiver, not durable remote delivery. See the
later contracts and worklog for validation and remaining integration gates.
[G](V0.14.5G-DISPOSABLE-FILE-RECEIVER-LAB.md) later tests a separate file-backed
receiver and retained-ID deduplication; it does not change D's volatile ledger
or authenticate the declared source.

The first D head `177655a` passed all 322 local Python tests but its
[HCC CI run](https://github.com/wojko6/Advanced-ASUS-Edge-Gateway-ZTNA-Infrastructure/actions/runs/41052311170)
failed the pre-existing `test_source_exception_failure_releases_lock` with an
empty-body JSON decode error. That test did not record the HTTP status, so the
original empty response cannot independently prove a 503. Source inspection
found that response delivery can precede the handler's final lock release.
A new deterministic test gates release after the response and observes **503
with an empty body**, then 200 after release. Sequential source-result tests now
wait on the actual lock with a one-second bound and assert status before JSON.
This adds one case to the full suite (323); D still has 31 and A–D 118 cases.
No retry hides a response, and no HTTP/source lock or runtime handler was relaxed.
