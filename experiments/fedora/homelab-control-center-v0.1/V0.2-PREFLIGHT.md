## Optional read-only source preflight — manual operator invocation only

The optional tool uses Python 3 standard library, `ss`, and `systemctl` if present. It performs **no configuration writes**, uses no environment credentials and prints no raw labels, log lines or private addresses.

```bash
cd ~/Pobrane/homelab-control-center-v0.1
python3 -B tools/fedora-v02-readonly-preflight.py --self-test
python3 -B tools/fedora-v02-readonly-preflight.py --inspect
# Optional after inspecting the exact source: bounded loopback HTTP GETs.
python3 -B tools/fedora-v02-readonly-preflight.py --run
```

- `--self-test` checks synthetic parsing and output policies; no host query or HTTP.
- `--inspect` checks service active states and parses `ss -H -lnt` for port 8428 (VM) and 3100 (Loki), displaying only coarse verdicts. If `ss` is missing, the result is `UNKNOWN`.
- `--run` refuses root and warns/holds on any non-loopback listener detected for these ports. It then issues at most **three GETs to 127.0.0.1 only**: VM `/health`, VM `/api/v1/query` with the fixed `count(up)` expression, and Loki `/ready`.
- Network I/O: no redirects, no proxy, 2-second per-request timeout and 16-KiB response cap. No raw labels, metric series, or Loki logs are printed.
- `count(up)` counts series, not how many have `up=1`; it does not establish freshness, full service health or alert delivery. HTTP 200 from Loki `/ready` is readiness, not proof of log ingestion.
- A missing service, 401/403, timeout, malformed JSON or unavailable metric is reported; the tool never tries to repair or reconfigure anything.
- **Operator ran this bounded script and a separate set of aggregate instant queries** (see dated observations); do not infer full runtime acceptance or UI integration.

## Proposed narrow adapter contract (requires later approval)

The browser must **never** receive a bearer token, Grafana cookie, shell access, filesystem path, router management credential or access to an arbitrary URL-proxy endpoint. In a later approved phase, a non-root **Fedora loopback-only** server would issue fixed, size-limited queries to individually approved local services; the app would receive only validated and sanitized status records.

1. **Queries are fixed:** every metric and Loki selector explicitly reviewed. No browser-provided PromQL/LogQL, URL, target name, label regex, time-span override, file path or command.
2. **Performance limits:** short timeout; tight sample and response-size caps; fixed concurrency/rate limit; no heavy full-range log scans or high-cardinality labels. Operator must select concrete values after source inventory.
3. **Freshness and coverage:** UTC observation times, per-source TTL based on real cadence, explicit `UNKNOWN/STALE/OFFLINE` policy. No universal 30-second freshness rule.
4. **Failure model:** timeout, 401/403, 5xx, malformed data, partial source failure or disconnection fail closed to `UNKNOWN` or `STALE`, never last-known `OK` indefinitely.
5. **Control plane:** no generic HTTP proxy, dynamic target registration, SMTP/Telegram test, restart/update button, DNS/firewall/router mutations or scheduled synthetic failure.
6. **Security:** no new public/LAN/Tailscale listener; loopback-only plus least privilege; no host/root API; no secrets in Git, browser, logs or exported reports. Authentication needs independent review if remote access is ever proposed.
7. **Rollback:** disabling connector must return app to existing **DEMO** state without changing monitoring/alerting; no new database or invasive router dependencies.
