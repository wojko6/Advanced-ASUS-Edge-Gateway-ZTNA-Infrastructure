# Network DNS Visibility / Client Activity Analytics

**Status:** planned. No live deployment or validation is claimed by this document.

Tracking issue: #108.

## Goal

Extend the existing edge-gateway observability stack with privacy-conscious
visibility into DNS activity generated by home-network clients.

The module is intended to show **domain-level DNS metadata**, not complete web
browser history.

Planned questions include:

- which domains were queried;
- when queries occurred;
- which local client generated them;
- which DNS record types are common;
- which clients or domains generate unusual query volume;
- which requests were blocked where that state can be derived reliably;
- where visibility disappears because a client bypasses the local resolver
  using encrypted DNS.

## Privacy boundary

The module must not rely on HTTPS interception.

Out of scope:

- TLS MITM;
- installing a decryption CA on household clients;
- full HTTPS URLs or URL paths;
- page contents;
- request bodies;
- cookies;
- credentials;
- payload capture as a normal analytics mechanism.

Raw browsing-domain activity is private operational data. Public repository
evidence must use sanitized or synthetic client/domain values.

## Proposed architecture

```text
home clients
    |
    | DNS
    v
ASUS / dnsmasq
    |
    | reuse existing logging path where possible
    v
router syslog-ng
    |
    | Tailscale + mTLS
    v
Fedora syslog-ng
    |
    | local ingestion
    v
Grafana Alloy
    |
    v
Loki
    |
    v
Grafana
```

The design deliberately keeps indexing, storage and visualization off the
512 MiB router.

The preferred implementation reuses the already validated syslog-ng +
Tailscale + mTLS transport instead of introducing another network-facing log
transport.

## Phase 0 — read-only preflight

Before installing Loki or changing router logging:

1. verify the current dnsmasq query-log configuration;
2. identify whether query lines already enter the existing centralized logging
   path;
3. inspect the exact query format available on the reference router;
4. measure approximate log volume;
5. confirm which client identifier is available;
6. determine whether a second router-side file source is necessary.

No duplicate forwarding path should be added unless the preflight demonstrates
that the current transport does not contain the required DNS events.

## Phase 1 — DNS event transport

If DNS events already traverse the current syslog-ng path, keep the router
unchanged and filter/parse them on Fedora.

If they do not, add the smallest practical read-only syslog-ng source for the
existing dnsmasq log and forward it through the same mTLS destination.

Requirements:

- backup before router change;
- syntax validation before restart;
- rollback path;
- no second TLS listener or parallel collector unless technically required;
- bounded router resource impact;
- no publication of real browsing data.

## Phase 2 — Fedora analytics backend

Planned components:

- Loki for local log storage/query;
- Grafana Alloy for local log ingestion;
- existing Grafana for visualization.

Loki should remain bound locally unless a separately reviewed access
requirement appears.

### Label-cardinality rule

Do not use high-cardinality values such as full domain names or individual
client IPs as persistent Loki labels.

Prefer low-cardinality labels such as:

- source;
- job;
- router role;
- DNS query type when useful.

Client and domain values should normally remain parsed log fields available at
query time.

## Phase 3 — Grafana dashboard

Planned views:

- DNS queries over time;
- top queried domains;
- query volume by client;
- DNS record types;
- blocked versus allowed queries when reliably known;
- clients with unusual query-rate spikes;
- recent DNS activity;
- visibility gaps associated with encrypted DNS.

The dashboard must clearly describe DNS activity as **resolver visibility**, not
as complete web-history capture.

## Phase 4 — encrypted-DNS coverage

This module is intentionally linked to issue #68.

The measurement-first bypass assessment should test:

- browser/application DoH;
- DoQ / QUIC;
- application-specific encrypted resolver paths;
- VPN-carried DNS;
- IPv6 resolver paths.

Missing events caused by these paths are a finding, not a reason to silently
claim complete client visibility.

Enforcement, if ever adopted, is a later decision after measurement,
false-positive analysis and rollback planning.

## Phase 5 — retention and resilience

Before calling the module complete:

- define local Loki retention;
- measure storage growth;
- verify restart/reboot persistence in a controlled window;
- document backup/rollback;
- validate that log ingestion recovers after a short outage;
- document any client-to-name alias mapping and keep personal aliases private.

## Acceptance criteria

The module can be marked completed only when:

1. DNS events from at least two controlled clients are distinguishable.
2. Timestamp, client and queried domain are parsed reliably.
3. Events reach Fedora through the existing protected transport or a documented
   equivalent.
4. Loki/Alloy storage and ingestion remain off-router.
5. Grafana can show DNS activity over time and by client/domain.
6. No HTTPS interception is used.
7. Encrypted-DNS visibility limitations are demonstrated explicitly.
8. Public evidence is sanitized.
9. Resource impact and retention are documented.
10. Rollback is documented and tested.

## Portfolio value

The completed module would extend the project from infrastructure monitoring
into lightweight network-activity analytics:

```text
edge security
+ metrics
+ alerting
+ centralized logs
+ DNS activity analytics
```

It should still be described as a home/SOHO lab feature rather than enterprise
network detection and response.
