## 4. Recovery, collisions and production safety gates

- A **read-only** ASUS inventory and off-router archive verification preserved **five required plus two optional** critical files; checksums and package rollback manifests matched. Existing live Unbound Manager `S61unbound` and active configuration matched the recorded baseline; KSK `38696` was present in the active trust anchor.
- The real `opkg` lab confirmed that `S61unbound` is **package-owned, not a conffile** and gets overwritten on upgrade **and** downgrade. The Manager script must be restored **before** starting the service. The edited packaged `unbound.conf` was preserved with an `-opkg` sidecar; the legacy packaged `root.key` is unprotected, while the Manager active trust anchor is a different path.
- Bounded read-only production tests showed Unbound on local port 53535, dnsmasq and Pi-hole responding on port 53, and `S61unbound` delegating control to `rc.func`. Its start pathway invokes a dnsmasq restart; a blind service `restart` is **not** the accepted maintenance procedure.
- DNS Guard scheduling and `crond` process were observed, but no watchdog entries were seen in the sampled syslog. **Last successful watchdog execution and DNS continuity during an Unbound stop were not demonstrated.** No live failover was initiated.
- Final **Fedora-only** release staging passed: five new IPKs, five rollback IPKs and the Manager start-script restore source hash-checked. **No files transferred to ASUS, no package installation or service restart.**
