## AUDIT-02 — exit-node NAT ownership

A controlled live validation was performed to determine the actual IPv4 NAT ownership for Tailscale exit-node traffic.

The validation confirmed:

- IPv4 forwarding was enabled;
- traffic arriving on `tailscale0` was evaluated by the project-owned `EDGE_TS_FORWARD` policy;
- the project exit-node forwarding rule admitted the controlled traffic toward the active WAN;
- Asuswrt-Merlin supplied the effective WAN `POSTROUTING` `MASQUERADE` rule;
- the platform parent `FORWARD` policy supplied the established/related return path;
- the same fixed-ID ICMP flow was correlated on `tailscale0` before NAT and on the WAN interface after NAT.

The resulting ownership boundary is therefore project-owned forwarding plus platform-owned WAN NAT. No duplicate project-owned `MASQUERADE` rule was added.

Sanitized evidence: `../../evidence/2026-09-22/audit-02-exit-node-nat-validation.md`.

AUDIT-02 was marked **CLOSED / LIVE VALIDATED** and merged through PR #50.

## Exit-node health-check contract

The live AUDIT-02 result exposed a runtime dependency on platform-owned Asuswrt-Merlin WAN NAT and return-path rules. That dependency was converted into explicit repository health-check logic.

When `EDGE_ENABLE_EXIT_NODE=1`, `scripts/healthcheck.sh` now verifies:

1. a valid WAN interface can be resolved;
2. IPv4 forwarding is enabled;
3. the project-owned exit-node forwarding rule targets the active WAN;
4. the platform provides effective WAN `MASQUERADE` or `SNAT`;
5. the parent `FORWARD` chain contains an established/related return path before the relevant WAN drop.

A focused regression test, `tests/test-healthcheck-exit-node-contract.sh`, was added. It exercises accepted and rejected rule shapes including missing forwarding, missing NAT, missing return path, misordered return-path rules, and both `MASQUERADE` and `SNAT` cases. The test was wired into GitHub Actions.

The implementation was merged through PR #51.

This PR was repository-only at merge time: it did not itself apply the new health-check script to the router, restart the firewall, bounce WAN, or reconfigure Tailscale.

## Legacy NAT hook cleanup and drift hardening

A read-only inspection of the live NAT parent chain found two direct classic-DNS redirect rules on the Tailscale interface in addition to the project-owned `EDGE_TS_PREROUTING` jump. Both direct rules had zero packet/byte counters, while the managed chain carried the active UDP/TCP DNS traffic.

The source was an old `/jffs/scripts/nat-start` hook containing only the two direct DNS redirects. The hook also had mode `0777`, which is unnecessarily permissive for a firmware-executed JFFS hook.

Controlled cleanup:

- verified and hashed the legacy hook before change;
- copied it into the private ASUS Edge backup area and reduced the backup copy to mode `0600`;
- removed the legacy `nat-start` from the active JFFS hook directory;
- deleted the two duplicate direct runtime redirects from the parent `PREROUTING` chain;
- preserved the single project-owned `tailscale0 -> EDGE_TS_PREROUTING` jump and the managed DNS redirects inside that chain;
- reran the deployed health check, which completed with `0 failure(s), 0 warning(s)` and `HEALTHCHECK_RC=0`.

No DNS resolver, Tailscale, WAN, or Unbound configuration was changed by this cleanup.

A follow-up health-check hardening change adds regression-tested detection for direct exact-interface Tailscale NAT rules outside the managed chain and for active JFFS hooks that are symlinked or group/world writable.

## DNS-over-TLS (DoT/853) bypass and blocking prototype

After production classic-DNS enforcement was live validated, Fedora was used to assess direct DoT on TCP/853.

With the workstation on the normal LAN path, a baseline TLS connection to `8.8.8.8:853` succeeded using TLS 1.3 and a verified `dns.google` certificate. This demonstrated that classic TCP/UDP 53 enforcement does not control DoT.

A temporary non-persistent `EDGE_LAN_DOT_TEST` chain was attached to `FORWARD` for `br0` and configured with:

```text
-p tcp --dport 853 -j REJECT --reject-with tcp-reset
```

During the blocked phase the Fedora client received `Connection refused`. A repeated controlled test was correlated with the router counter:

```text
1 packet / 60 bytes -> REJECT tcp dpt:853 reject-with tcp-reset
```

The test policy was then removed. The same TLS connection to `8.8.8.8:853` succeeded again, completing the A/B/A rollback validation.

The result supports an opt-in production DoT control. It does not establish control over DoH, DoQ, VPN-carried DNS, IPv6 DNS, or application-specific encrypted resolver transports.

Sanitized evidence: `../../evidence/2026-09-22/dot-853-block-prototype-validation.md`.

## LAN classic-DNS enforcement prototype

The previously documented LAN DNS bypass was re-tested with an isolated, non-persistent NAT policy.

The first Fedora attempt did not exercise the LAN path because policy routing sent `8.8.8.8` through the ASUS Tailscale exit node. After disabling exit-node use on Fedora, `ip route get 8.8.8.8` resolved through the normal LAN gateway on the workstation Wi-Fi interface.

A temporary `EDGE_LAN_DNS_TEST` chain was attached only to `br0`. It returned traffic already addressed to the router DNS endpoint and redirected other TCP/UDP port-53 traffic to the router resolver.

Controlled external-DNS queries then incremented both redirect rules:

```text
UDP/53 external-DNS redirect: 1 packet
TCP/53 external-DNS redirect: 1 packet
```

The temporary chain was removed immediately after validation and its absence was verified.

This supports an opt-in production implementation for classic LAN DNS enforcement. It does not establish control over DoH, DoT, DoQ, VPN-carried DNS, IPv6 DNS, or other encrypted resolver transports.

Sanitized evidence: `../../evidence/2026-09-22/lan-dns-enforcement-prototype-validation.md`.

## DNS-filtering roadmap and Pi-hole design candidate

The roadmap was expanded with a post-observation Pi-hole + Unbound migration concept.

The proposed design keeps Unbound as the recursive validating resolver, preserves firmware dnsmasq for DHCP/local-name duties on a non-53 port, and considers Pi-hole as a potential replacement for Diversion for filtering, observability, and per-client policy.

This remains a **design candidate only**. Pi-hole was not installed or deployed on the reference router during this session.

The acceptance plan was adjusted to normal router usage: repeated clean startup/power cycles, normal-use sessions, WAN reconnect handling, Gravity maintenance, RAM/swap behavior, health checks, rollback, and DNS-path validation are emphasized instead of requiring a new continuous 7-14 day gate.

## Diversion A/B/C filtering validation

After the stability observation was closed, a controlled Diversion comparison was performed on the reference router.

Three states were tested:

```text
A. Standard + snbAdSupport=yes
B. Standard + snbAdSupport=no
C. Large + snbAdSupport=no
```

### Variant A — Standard + SNBForums support enabled

The active configuration included a hard-coded allowlist exception for `pagead2.googlesyndication.com`. That exception overrode the broader `googlesyndication.com` block for the tested host.

### Variant B — Standard + SNBForums support disabled

Diversion's own configuration menu was used to set:

```text
snbAdSupport=no
```

The tested `pagead2.googlesyndication.com` exception disappeared and DNS blocking improved for the sample.

The Android LTE/5G -> Tailscale -> ASUS classic-DNS path was re-checked after this change. The project UDP/53 REDIRECT counter increased for a controlled query and a repeated unique query was observed between dnsmasq and Unbound on loopback port 53535.

Result: the previously validated classic-DNS path remained healthy.

### Variant C — Large + SNBForums support disabled

Diversion was changed to the `Large` profile while keeping `snbAdSupport=no`.

The status screen reported approximately 246k blocked domains. Multiple advertising and RTB-related domains returned `NXDOMAIN`, but visible advertising still remained on representative real-world sites including `dobreprogramy.pl` and `ithardware.pl`.

This demonstrated that broader DNS-domain blocking does not equal complete browser-content or in-app ad removal.
