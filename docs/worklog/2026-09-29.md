## Issue #127 — LAN management / WAN exposure hardening

The controlled post-audit hardening round began with issue #127.

Read-only inspection established that WAN WebUI access and WAN ping were
disabled, SSH was LAN-only on the configured non-default port, Port Trigger and
DMZ-host were inactive, and UPnP/NAT-PMP had no active runtime daemon/listeners
or dynamic mappings. A stale static port-forward remained, however: WAN TCP
20/21 was still mapped to SSH/22 on an inactive LAN host with no current DHCP or
static-client record.

The original static-forward values were captured for rollback before changing
state. The stale forward was removed, port forwarding was disabled, the
firewall was rebuilt, the project Tailscale chains remained intact, and the
project health check completed with:

```text
Summary: 0 failure(s), 0 warning(s)
HEALTHCHECK_RC=0
```

For normal-LAN administration, the Fedora workstation's stable per-SSID MAC
behavior was verified and a dedicated DHCP reservation was installed. ASUS
`ACCESS_RESTRICTION` was then enabled for that one administration host with
WebUI + SSH access. The generated firewall policy permits HTTPS/8443 and
SSH/1122 from the authorized host and ends with a default DROP before the
platform's general LAN accept rule.

Validation passed in both directions:

- a fresh SSH session from the authorized Fedora host succeeded;
- the router WebUI returned HTTP 200 from the authorized Fedora host;
- controlled HTTPS and SSH attempts from a temporary non-admin LAN source
  timed out;
- the temporary test address was removed immediately after the negative test;
- the `ACCESS_RESTRICTION` DROP rule accumulated 10 packets / 600 bytes;
- a final authorized SSH/WebUI recheck passed;
- normal GeForce NOW use remained functional after the hardening.

Sanitized evidence is recorded in
`evidence/2026-09-29/issue-127-lan-management-wan-exposure-hardening.md`.
