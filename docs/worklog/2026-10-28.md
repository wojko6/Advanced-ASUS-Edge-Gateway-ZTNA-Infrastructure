- **Gate:** bounded Fedora client acceptance **PASS**. Full workstation reboot and sustained soak not performed.

## ASUS GNUton ARMv7 — 1.104.2 → 1.104.4

- **Initial production preflight:** CLI and daemon 1.104.2, hashes matched known-good October 21 deployment, Entware disk available and full project `healthcheck.sh` reported **0 failures, 0 warnings**. Entware package metadata remained **1.96.1-1**, older than the custom running version; `opkg upgrade tailscale` was deliberately avoided.
- **Source and build:** upstream Tailscale tag `v1.104.4`, pinned commit `27047635f237d1f3e0b08c0f487674757f30d2f7`, Go 1.27.3, `CGO_ENABLED=0`, `GOOS=linux`, `GOARCH=arm`, `GOARM=7`; both binaries built with upstream `build_dist.sh` on Fedora. The first toolchain check correctly held at Fedora's existing Go 1.26.10; isolated Go 1.27.3 was then used without replacing the host Go.
- **Off-router gates:** both new binaries matched expected SHA-256; ARMv7 QEMU version smoke checks **PASS**. An isolated rootless QEMU ARM daemon opened a local IPC socket and responded to the new CLI (`NeedsLogin` expected without credentials); `IPC_LAB=PASS`, with no tailnet login or production network contact. Emulation does not prove real forwarding.
- **Staging:** an independent LAN SSH management path was verified. Previous router binaries were copied and hash-verified in private backup storage; new pair transferred, checksummed and executed natively as version commands. The original active daemon and on-disk live binaries were confirmed unchanged before the actual deployment.
- **Live change:** explicit operator-approved paired binary replacement and project-managed `services-start` Tailscale maintenance restart, retaining node identity and a private state backup. The running daemon's executable hash matched the 1.104.4 candidate; both CLI and daemon reported 1.104.4. The post-deployment project healthcheck reported **0 failures, 0 warnings**, including Tailscale online, `tailscale0`, auto-update off, native netfilter off, exit-node IPv4 forwarding/NAT via WAN, managed firewall and source-scoped Pi-hole, Unbound DNSSEC and DNS Guard checks. Fedora peer reachability **PASS**.
- **Result:** `DEPLOYMENT_GATE=LIVE_VALIDATED`, known-good 1.104.2 binaries retained for manual recovery, no rollback invoked. No full router reboot, power-loss, extended stability or deliberately exercised rollback test.

## Functional Android acceptance — Pi-hole and exit node

- A unique DNS query from the Android Tailscale client was visible in Pi-hole Query Log (A and HTTPS record types); the client identity matched `tailscale status`. `Served from cache` demonstrated query servicing, while a subsequent **`Blocked (gravity)`** entry confirmed actual Gravity filtering for that same client. This extends the earlier [October 6 source-scoped Pi-hole validation](../../evidence/2026-10-06/issue-152-android-pihole-tailscale-validation.md) in the tested conditions; it does not prove every alternative Android DNS path.
- **Actual LTE/5G exit-node smoke:** without the ASUS exit node, phone public IPv4 differed from home WAN; with ASUS selected, public IPv4 matched the Fedora home WAN and web pages loaded. This verifies tested IPv4 Internet egress through the ASUS, beyond a mere process or firewall check. Public client/WAN addresses are deliberately omitted.
