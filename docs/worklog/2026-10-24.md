# Engineering worklog — 2026-10-24

> **Scope:** sanitized October 24 ASUS/Entware Unbound 1.26.2 maintenance incident, Fedora ARMv7 labs and later successful production R2 deployment. Operator-reported results; not a complete record of other engineering on this date.
> **Production change:** initial failed five-package 1.26.2 upgrade and rollback to 1.26.1, targeted automatic trust-anchor relocation and successful recovery, followed **later the same day** by an authorized controlled R2 five-package upgrade to 1.26.2.
> **Final observed production state:** **1.26.2-1 (5/5)**, D1/D2 PASS, direct Unbound DNSSEC positive AD and bogus SERVFAIL on **UDP and TCP**, router dnsmasq/Pi-hole DNS PASS. DNS Guard live failover and ASUS cold-reboot persistence remain **NOT TESTED**.

## 1. Upgrade attempt, outage and rollback — actual ASUS

- The earlier [October 23 off-router release-readiness](../operations/unbound-1.26.2-armv7-release-readiness-2026-10-23.md) concerned build artifacts and bounded tests. The October 24 work **did** include an explicitly authorized on-router upgrade attempt; the two dates must not be conflated.
- After a successful read-only preflight, packages and the preserved Manager startup script were hash-staged to a private router location. Five real `1.26.2-1` packages were installed.
- Short initial startup checks were misleading: Unbound quickly disappeared and the subsequent independent DNSSEC gate failed.
- Five original `1.26.1-1` packages were restored with the original startup Manager, but the process again exited shortly after startup. Basic package and `unbound-checkconf` success did **not** prove resolver availability.
- A bounded foreground diagnostic identified fatal refusal to create a temporary automatic DNSSEC trust-anchor file inside the chroot: `Permission denied`.

## 2. Targeted production recovery — actual ASUS

- Confirmed the service uses an unprivileged account while the chroot root is `root:root 0755`; the original anchor file was itself writable, but the parent directory was not writable by the daemon.
- Backed up the original active configuration/anchor, added a dedicated unprivileged-owned writable anchor directory (`0700`) with a restricted anchor copy (`0600`), and changed **only** the active `auto-trust-anchor-file` path. The chroot root's mode was not loosened, and DNSSEC stayed enabled.
- One existing Manager start succeeded. The service and TCP/UDP sockets remained present through a 38-second observation, followed by independent read-only post-rollback DNS/DNSSEC checks.
- Direct Unbound TCP positive DNSSEC **AD** and negative DNSSEC **SERVFAIL** passed; the router DNS and Pi-hole client paths passed UDP/TCP **4/4**.
- Read-only runtime gate V1 passed seven negative predicate self-tests and a further **60-second unchanged process-identity** observation. There was no additional restart or package installation during that gate.

## 3. Fedora-only diagnosis and reproducible `opkg` behavior

- Verified the October 23 pre-upgrade config/anchor backup by SHA-256. It includes the anchor file but **not the chroot directory metadata**, so pre-upgrade production directory ownership remains unknown.
- Inspected 10 real IPKs. Both `unbound-daemon` 1.26.1 and 1.26.2 explicitly package the chroot root directory as `0:0 0755`; therefore this is **not solely a 1.26.2 package metadata change**.
- The first isolated rootless-Podman attempt stopped during synthetic directory setup due to missing container file-ownership capability; no upgrade was tested in that failed harness run.
- Corrected V2, using the real ASUS ARMv7 `opkg` executable and SHA-validated IPKs, reproduced normalization of a pre-existing synthetic `65534:65534 0700` chroot directory to `0:0 0755` during **both** upgrade and downgrade. Each real package transaction returned RC=0 with five expected packages.
- A dedicated synthetic anchor directory (`65534:65534 0700`) and anchor file (`0600`) retained ownership, mode and contents through both transactions. Modified package conffiles were preserved and corresponding `-opkg` sidecars appeared.
- The container had no network/host binds and used nine synthetic *dependency database entries*, not full runtime libraries: this evidence proves `opkg` file/metadata behavior, **not** working ARMv7 Unbound 1.26.2 or independent DNSSEC on that version.

## 4. Historical evidence boundary after the first failed attempt

The initial restoration to 1.26.1, direct TCP DNSSEC recovery, and 60-second identity gate were real but **not** proof of 1.26.2 runtime acceptance. The isolated real-`opkg` metadata reproduction did **not** reveal the unknown pre-upgrade production directory owner/mode. At this *earlier* point, the correct status was 1.26.2 HOLD. Later results below supersede that *deployment status*, not the incident record.

- All four were independent, rootless, off-router labs. They do not retroactively change the original incident results.

## 6. Later successful ASUS R2 upgrade and final bounded acceptance

- Read-only investigation found active `auto-trust-anchor-file` pointing into the restricted, service-owned `dnssec-auto` directory. The historical, no-longer-active chroot-root key was **not** copied over the active anchor.
- Corrected R2 tooling retained the earlier rollback directory/journal. Verified ten offline upgrade/rollback IPKs and custom Manager in an entirely separate private staging directory, with manifest **11/11 PASS**.
- Repeated 1.26.1 baseline verified direct TCP signed DNSSEC `AD`, bogus `SERVFAIL`, router dnsmasq and Pi-hole client queries — PASS. Fresh D0 verified 5/5 old packages, custom Manager, live sockets, active anchor owner/mode, DNS Guard schedule and disk margin — PASS.
- Attended real ASUS D1: `OPKG_UPGRADE_RC=0`, five Unbound packages reached `1.26.2-1`, custom `S61unbound` restored with expected hash/owner/mode, daemon started and basic listener gate PASS. `D1_RESULT=PASS_1262_RUNNING_AWAIT_D2_DNSSEC`.
- Independent read-only D2: `D2_RESULT=PASS_TCP_DNSSEC_AND_CLIENT_DNS`, direct Unbound TCP good `AD=1` and bad `SERVFAIL`, router dnsmasq and Pi-hole client queries — all PASS.
- Subsequent direct **real-router UDP** Unbound queries: `UNBOUND_1262_DIRECT_UDP_AD1=PASS` and `UNBOUND_1262_DIRECT_UDP_SERVFAIL=PASS`. No file writes or service restarts in this final UDP check.
- No rollback was required for the successful R2 deployment. Preserve both R2 recovery materials and the **previous** failed-maintenance history, outside public Git.

## 7. Final decision and explicit evidence limits

**Closed for the authorized package change:** production Unbound **1.26.2-1**, 5/5, D1 PASS; D2 TCP DNSSEC and client DNS PASS; independent direct UDP DNSSEC AD/SERVFAIL PASS. This is not evidence of uninterrupted DNS during the controlled stop.

**Open and separate:** active DNS Guard failover under deliberate outage, cold-router reboot and persistence, RFC 5011 real 30-day promotion, long soak and broader disaster-recovery. The historical production pre-upgrade chroot metadata are still unknown. Do not reopen the package upgrade just to test those independent gates.
