## 6. Tailscale Fedora package-source migration and firewall correction

- Prepared and verified the signed original Fedora **1.98.8** rollback RPM and Tailscale vendor **1.104.2** RPM, including issuer key fingerprint and an isolated signature check. A planned DNF transaction contained only the one package upgrade. The prior Fedora unit differed from the vendor unit in executable path, default environment and explicit firewall selection.
- The first attempt to install a local RPM with `localpkg_gpgcheck=true` failed because the `@commandline` source lacked a configured signing key; **no installation occurred in that failed attempt**. The operator then used a **temporary, verified official vendor repository definition** with normal package GPG checking. The package transaction succeeded and the daemon restarted; Tailscale remained online with a direct connection to the gateway.
- **Initial regression:** the replacement unit omitted the Fedora package's `TS_DEBUG_FIREWALL_MODE=auto`, leading to default `iptables` selection and a failed `CONNMARK` workaround under Fedora's `iptables-nft`/firewalld combination. This appeared in the Tailscale health report even though the tunnel still responded.
- An explicitly backed-up, **Fedora-host-only** setting `TS_DEBUG_FIREWALL_MODE=auto` was restored in the vendor defaults file, followed by a controlled `tailscaled` restart. Follow-up logs selected **nftables** (243 nftables rules detected, zero iptables rules), with **no prior CONNMARK error in current health**, backend `Running`, self online, active firewalld, **direct gateway ping 2 ms**, and no error-level service journal entries. The pre-existing `accept-routes=false` advisory remains expected.
- **Follow-ups:** the temporary vendor repository was **not** permanently installed, and the post-migration configuration was **not** tested across a subsequent Fedora reboot. Do not assume full routing/DNS/firewall-path coverage from a single ping. No ASUS settings, route-acceptance, exit-node choice or DNS policy were changed.
