# Worklog — 2026-09-30

## Management WebUI split-DNS / HTTPS closure

The router-management HTTPS path was cleaned up after testing the local
`router.home.arpa` convenience name.

The local name reached the router, but Chromium rejected WebUI static resources
with `ERR_CERT_COMMON_NAME_INVALID`. Certificate inspection confirmed that the
active Let's Encrypt certificate covered the router's ASUS DDNS hostname rather
than `router.home.arpa`.

A direct hostname-to-`192.168.50.1` `curl --resolve` test verified the
certificate successfully and returned `HTTP/1.0 200 OK`. The same hostname then
loaded the full ASUS WebUI correctly in the browser.

The accepted design uses a Pi-hole local DNS record that resolves the
certificate-covered ASUS DDNS hostname to `192.168.50.1`. Temporary
`/etc/hosts` overrides were removed, resolver caches were flushed, and the
final Fedora checks returned:

```text
getent hosts <router-ddns>.asuscomm.com
192.168.50.1    <router-ddns>.asuscomm.com

curl -I https://<router-ddns>.asuscomm.com/
HTTP/1.0 200 OK

HOSTS_CLEAN
```

The public repository redacts the deployment-specific DDNS label.

Sanitized validation is recorded in
`evidence/2026-09-30/management-webui-split-dns-https-validation.md`.
## Personal Cloud automated sync acceptance (#136)

The Fedora-to-router Personal Cloud v1 path was completed and live-validated.
The workstation now synchronizes `~/RouterCloud/` to the dedicated
`ROUTER_DATA/RouterCloud/` SSD directory with `rsync -rtv` over the existing
non-default SSH service. A user `systemd.path` trigger accelerates top-level
changes and a five-minute `systemd.timer` provides reconciliation.

Negative testing exposed two important SSH edge cases and both were corrected.
First, OpenSSH could fall back to the workstation's ordinary default key when
the dedicated RouterCloud key file was absent; the final client uses
`-F /dev/null`, `IdentityFile=none`, `IdentityAgent=none`, explicit public-key-only
authentication, and the dedicated `-i` identity. Second, a test that layered a
new `rrsync` forced command onto the pre-existing project wrapper produced two
`command=` options after Asuswrt-Merlin regenerated `authorized_keys`, causing
Dropbear to reject the key. The final persistent key record contains exactly
one forced command: the project-owned `personal-cloud-rsync` wrapper.

The final acceptance passed controlled copy, local-delete safety, deliberate
authentication failure, recovery after restoring the key, arbitrary-shell
denial, SSH-service regeneration, a full router reboot, post-reboot transfer,
and a final automatic `systemd.path` transfer. The browser UI remains separate
work under #137 and versioned snapshots remain separate work under #138.

Sanitized evidence is in
`evidence/2026-09-30/issue-136-personal-cloud-sync-validation.md`; the
source-controlled client, wrapper and units are documented in
`docs/personal-cloud-sync.md`.

## Personal Cloud browser-access baseline (#137)

The browser-access work moved from pilot to a reboot-validated LAN/Tailscale
baseline. Dufs 0.46.0 now serves only the dedicated RouterCloud SSD directory on
a separate LAN alias and HTTPS port 443 with dedicated authentication,
`allow-delete: false` and symlinks disabled.

A real remote Fedora test over a phone hotspot proved the subnet route,
source-scoped `EDGE_TS_INPUT` rule and HTTPS health response. The accepted
connection incremented the dedicated RouterCloud firewall counter without
opening router SSH.

A reboot exposed an Entware/data-volume mount-order race. The final startup
path defers when `ROUTER_DATA` is absent and retries from the later post-mount
event. A subsequent clean reboot reproduced the race and recovered
automatically. An executable backup accidentally left under
`/opt/etc/init.d/S67*` was moved out of the init directory so `rc.unslung`
cannot execute it as a second service.

Remote name resolution was then completed with a firmware-dnsmasq
`cloud.home.arpa` record plus Tailscale restricted/split DNS for
`home.arpa`. The initial remote Fedora acceptance used the router Tailscale
DNS listener. During the later Android troubleshooting, the restricted
`home.arpa` nameserver was changed to the router LAN DNS address reachable
through the advertised subnet route; that final split-DNS form was validated
from the Android client over LTE/5G. Unrelated DNS remains outside the
restricted domain scope.

Android/Poco acceptance was then completed with the project development
Tailscale client. Troubleshooting showed that the development client and the
previous official Android client were separate tailnet nodes. After enabling
Tailscale DNS plus subnet routes on the active development client and
allowlisting that active node identity, `https://cloud.home.arpa/` loaded over
LTE/5G. The source-scoped RouterCloud firewall counter increased on the mobile
connection. The obsolete Android client was removed and its stale RouterCloud
allowlist entry was removed as well.

The public RouterCloud CA certificate was installed in the Android trust store;
the browser then accepted the private TLS chain without a certificate warning
and dedicated RouterCloud authentication succeeded. Private CA key material
remains off-device and out of the repository.

Issue #137 remains open for safe rename design, storage-usage presentation,
explicit outside-root/WAN negative tests and the final custom UI.

`evidence/2026-09-30/issue-137-routercloud-browser-access-validation.md`.

## Personal Cloud v1 completion and evening configuration audit (#137)

The later RouterCloud acceptance completed the items that were still pending in
the earlier baseline entry. The project-patched Dufs 0.46.0 build passed safe
same-directory rename, destination-no-overwrite, cross-directory refusal,
root/traversal/symlink-escape negative tests, Polish UI validation, cache-busting
and native storage-capacity presentation. A clean reboot preserved the dedicated
RouterCloud address, service listener and hardened global delete/symlink policy.

The no-WAN check was also completed. The RouterCloud process remained bound only
to the dedicated LAN alias, no WAN DNAT to that alias was present, and a real
cellular test with Wi-Fi and Tailscale disabled could not reach the service.

A second authorized Android/Poco client was then aligned with the Fedora
administration workstation. Its normal-LAN address was given a stable DHCP
reservation and the ASUS access-restriction policy was extended with the same
management class as the workstation. RouterCloud LAN access was verified from
the phone. Over Tailscale, the stale identity left by the removed Android client
was removed and the active Android node received the same router-management and
RouterCloud source-scoped policy as Fedora. Both the ASUS WebUI management path
and RouterCloud path were verified over mobile data.

That test exposed a real configuration bug: the project used one
`EDGE_ROUTER_HTTPS_PORT` value both for the Tailnet-facing management ingress
and the local ASUS `httpds` destination. After the firmware WebUI listener had
moved to TCP/443, the old policy still generated `:8443 -> 192.168.50.1:8443`,
where no listener existed. The live configuration was corrected to keep 8443 as
the Tailnet ingress while DNAT targets the actual local TCP/443 listener.
RouterCloud remains separate on its dedicated alias TCP/443.

The live `/jffs/configs/asus-edge.conf` also contained many consecutive
duplicate lines from earlier maintenance. A backup was taken and the file was
deduplicated without changing intended values. The source-controlled example
was already clean. During the same audit, the obsolete Android Tailscale admin
source was removed.

The source tree was reconciled with these findings: the firewall now separates
management ingress and target ports, rejects a management/RouterCloud ingress
port collision and validates the new target port. The health check now verifies
the exact source-scoped management DNAT/INPUT policy, detects stale same-port
DNAT and stale pre-DNAT ingress ACCEPT rules, rejects unexpected RouterCloud
source rules, checks the dedicated RouterCloud listener, and verifies safe-move,
global-delete-off and symlink-off settings. Static guards cover those checks.
A source audit of the active example configuration, firewall, healthcheck,
WebUI status collector, evidence collector and RouterCloud templates found no
remaining duplicate direct variable assignments or consecutive duplicated
configuration entries in the source-controlled files.

Known remaining #137 work is deliberately narrow: trusted-device DELETE is not
implemented yet, global delete remains disabled, and the exact project-owned
Dufs patch set plus reproducible ARMv7 build recipe still need to be committed
before final closure. Direct access to the ASUS WebUI by Tailnet IP also shows a
certificate-name warning because the current management certificate does not
cover that Tailnet IP; the already validated certificate-covered hostname path
remains the preferred browser path.
