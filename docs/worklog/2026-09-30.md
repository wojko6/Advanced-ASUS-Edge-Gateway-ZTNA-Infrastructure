# Worklog — 2026-09-30

## Management WebUI split-DNS / HTTPS closure

The router-management HTTPS path was cleaned up after testing the local
`router.home.arpa` convenience name.

The local name reached the router, but Chromium rejected WebUI static resources
with `ERR_CERT_COMMON_NAME_INVALID`. Certificate inspection confirmed that the
active Let's Encrypt certificate covered the router's ASUS DDNS hostname rather
than `router.home.arpa`.

A direct hostname-to-`192.168.50.1` `curl --resolve` test verified the
certificate successfully and returned `HTTP/1.0 200 OK`. The same hostname then
loaded the full ASUS WebUI correctly in the browser.

The accepted design uses a Pi-hole local DNS record that resolves the
certificate-covered ASUS DDNS hostname to `192.168.50.1`. Temporary
`/etc/hosts` overrides were removed, resolver caches were flushed, and the
final Fedora checks returned:

```text
getent hosts <router-ddns>.asuscomm.com
192.168.50.1    <router-ddns>.asuscomm.com

curl -I https://<router-ddns>.asuscomm.com/
HTTP/1.0 200 OK

HOSTS_CLEAN
```

The public repository redacts the deployment-specific DDNS label.

Sanitized validation is recorded in
`evidence/2026-09-30/management-webui-split-dns-https-validation.md`.
## Personal Cloud automated sync acceptance (#136)

The Fedora-to-router Personal Cloud v1 path was completed and live-validated.
The workstation now synchronizes `~/RouterCloud/` to the dedicated
`ROUTER_DATA/RouterCloud/` SSD directory with `rsync -rtv` over the existing
non-default SSH service. A user `systemd.path` trigger accelerates top-level
changes and a five-minute `systemd.timer` provides reconciliation.

Negative testing exposed two important SSH edge cases and both were corrected.
First, OpenSSH could fall back to the workstation's ordinary default key when
the dedicated RouterCloud key file was absent; the final client uses
`-F /dev/null`, `IdentityFile=none`, `IdentityAgent=none`, explicit public-key-only
authentication, and the dedicated `-i` identity. Second, a test that layered a
new `rrsync` forced command onto the pre-existing project wrapper produced two
`command=` options after Asuswrt-Merlin regenerated `authorized_keys`, causing
Dropbear to reject the key. The final persistent key record contains exactly
one forced command: the project-owned `personal-cloud-rsync` wrapper.

The final acceptance passed controlled copy, local-delete safety, deliberate
authentication failure, recovery after restoring the key, arbitrary-shell
denial, SSH-service regeneration, a full router reboot, post-reboot transfer,
and a final automatic `systemd.path` transfer. The browser UI remains separate
work under #137 and versioned snapshots remain separate work under #138.

Sanitized evidence is in
`evidence/2026-09-30/issue-136-personal-cloud-sync-validation.md`; the
source-controlled client, wrapper and units are documented in
`docs/personal-cloud-sync.md`.
