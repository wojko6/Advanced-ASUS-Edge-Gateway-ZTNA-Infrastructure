# Engineering worklog — 2026-09-18

## Summary

This session combined Fedora clean-room Disaster Recovery validation, Zen/Fedora integration documentation, CI expansion, backup portability fixes, case-study organization, and preparation for post-Stability-Gate validation. The ASUS reference router was not intentionally reconfigured.

## Fedora clean-room Disaster Recovery

A Fedora recovery set was restored into a clean VMware test VM and successfully booted from the recovered virtual NVMe disk to the graphical desktop after the recovery ISO was detached.

The test confirmed the recovered root/home layout and restored boot filesystems. It also exposed practical target-adaptation requirements: /boot UUID references had to match the restored partition identity, and restored /boot content required SELinux relabeling. The VM-specific mcelog.service failure was documented separately and was not treated as a DR failure.

See ../FEDORA-DR-RESTORE-VALIDATION-2026-09-18.md.

## Fedora DR finalization helper and CI

The observed recovery fixes were converted into scripts/fedora-dr-restore.sh with dry-run/apply behavior, /boot UUID adaptation, GRUB UUID correction, SELinux relabeling, and configuration-file rollback.

The helper was then hardened to refuse / as a target, refuse a target backed by the same filesystem source as the running system, require exact target root, /boot and /boot/efi mountpoints, and use collision-resistant rollback-directory creation.

Focused Fedora DR tests were added and integrated into GitHub Actions. CI was later expanded so existing Python recovery, firewall mock/configuration, evidence-collector, and log-retention tests run directly in the workflow. Expanded validation completed successfully.

## Backup checksum portability

The router project backup sidecar checksum was changed to store the archive basename instead of an absolute path, allowing the archive and .sha256 file to be copied elsewhere and verified normally. Regression coverage was added.

## Zen Linux case study and evidence hygiene

A Fedora/GNOME Zen integration case study was added covering dynamic localhost proxy/PAC listeners, GNOME proxy lifecycle, loopback exposure, PAC behavior, the tested CLI curl limitation, and observed Fedora/Tailscale DNS behavior.

Deployment-specific LAN/Tailscale addresses, peer names, and the local username were sanitized while preserving technically relevant public-service examples.

## DNS enforcement gap and post-gate plan

The repository documented the LAN DNS enforcement gap observed during read-only validation: Tailscale-facing classic DNS has project-owned REDIRECT behavior, while ordinary LAN/Wi-Fi clients can still deliberately select an external classic resolver while DNS Director is disabled.

No router-side fix was deployed during the Stability Gate. A dedicated post-gate plan was added for closing the observation window, validating AUDIT-02 exit-node NAT, validating AUDIT-03 Fedora/Android DNS datapaths, and making changes only if the evidence demonstrates a real defect.

## Repository organization

A case-study index was added and surfaced from README. Roadmap, changelog, validation matrix, evidence timeline, IPv6 claim boundaries, syslog-ng wording, architecture-image references, and PROJECT-STATUS were synchronized with the actual repository state.

## End-of-day state

Fedora DR had a successful clean-room validation, the finalization helper was more strongly guarded and tested, CI coverage was broader, backup verification became more portable, and the repository had a clearer chronological/evidence structure. The router remained inside the unchanged-state Stability Gate.
