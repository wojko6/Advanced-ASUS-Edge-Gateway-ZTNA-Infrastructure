## 1. Fedora-only DNS outage and recovery

The operator reported normal internet reachability by IPv4 address (`ping 1.1.1.1` 2/2 successful) but failed or hung DNS name resolution on Fedora while a phone using the same ASUS Wi-Fi worked normally.

`resolvectl dns` displayed the deployment-local Wi-Fi Pi-hole resolver and Tailscale's standard resolver `100.100.100.100`; `resolvectl domain` showed a catch-all `~.` routing domain on `tailscale0`. The operator ran `sudo tailscale set --accept-dns=false`, reported that webpages loaded immediately and subsequently confirmed stable internet.

**Boundary:** observed recovery is strong evidence of a Fedora Tailscale DNS preference/integration issue, not evidence that ASUS Unbound, Pi-hole or the newly deployed router Tailscale binary was at fault. No router DNS/firewall change was instructed or reported. MagicDNS name resolution on this Fedora client may require a separate design if used later.

## 7. Issue #235 — separate Fedora security laboratory and authorized read-only ASUS inventory

The operator reported additional **separately scoped** RouterCloud / DUFS 0.46.0 trust-boundary tests on 2026-10-21. These are **not** changes to the running RouterCloud service. Source and build evidence remained limited to a pinned Fedora test snapshot; laboratory PASS does not grant deployment approval.

- **Browser/origin:** V2.30M real Firefox tests 15/15 self-tests, 10/10 E2E; V2.30N1 explicit Basic Auth and role checks 22/22, 19/19; V2.30O cross-origin write-effects 21/21, 19/19. The browser rejected cross-origin reads; an opaque `no-cors POST` response was *not* treated as proof the request was never sent. The tested file was unchanged. V2.30N initially held on a wrong internal asset URL. **V2.30P and P1 were SKIP**, since the Firefox HTTP Basic credential cache was not verified; general CSRF protection remains unproven.
- **Publisher/source:** V2.30Q found 16/16 expected static source indicators (12/12 self-tests) for staging, activation and rollback, but could not prove that the actual publisher has exclusive write authority.
- **Authorized production read-only sampling, V2.30R2 (2026-10-21, 18:36 UTC):** after two incomplete BusyBox metadata-provider attempts (R, R1), 24/24 expected filesystem metadata observations were collected. The process matched RouterCloud heuristically by both `comm` and executable basename, with **real/effective UID and GID 0** and broad `CapEff=0000003fffffffff`; binary SHA-256 and full supervisor provenance were not confirmed. The two SSD ext4 mount roots were `0777`; the protected Entware subtree and trusted asset directory were root-owned `0755`, and the four trusted UI files root-owned `0644`. The backup parent was `0777`, whereas its private dated child was `0700`. A point-in-time `/proc` scan of 147 processes and 879 FDs found no open writable descriptor under the **historically pinned** asset path; this is not evidence that future writes are impossible. Active `assets:` config mapping was deliberately **not** read.
- **Privilege/ancestry composition on Fedora:** V2.30S static/offline DAC review 30/30; V2.30T kernel user-namespace and sealed-config handoff 17/17 self-tests, 8/8 Publisher, 8/8 Untrusted, 16/16 HTTP, 7/7 integration. V2.30U ran a freshly snapshot-built, actual DUFS process as a nonroot role with zero capabilities; sealed `memfd` YAML was read through `/proc/self/fd/N` (23/23 self-tests, 11/11 child checks, 10/10 live tests). No production secrets or ASUS process were used.
- **Ancestor pathname test:** V2.30V 25/25 self-tests, 12/12 unprivileged kernel checks and 10/10 supervisor checks showed a synthetic, non-mountpoint `0777` parent permits renaming/replacement of a protected descendant name, while `0755` or `1777` rejected that operation. An already-open FD continued reading the original inode. **This is not proof that an actively mounted ASUS ext4 mountpoint can be renamed.**
