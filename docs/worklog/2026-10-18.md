## 1. Production read-only evidence — direct Cron attribution

1. The scoped root-Cron inventory returned **three jobs** and **two directly referenced JFFS scripts**. Both scripts passed bounded file metadata checks. One had nonroot UID and GID plus its owner-write bit; ancestor write hints were zero in the measured scope. This is **not** a proof of inaccessible ownership or trusted parent-chain lifetime.
2. The V2.6 firmware-local account lookup found no entries for the anomalous numeric owner/group in the inspected local files. The V2.7–V2.7.1 *fixed Entware account candidates* were `UNAVAILABLE`, **not** `MISSING`. These observations cannot prove the owner ID does not exist, cannot execute later or lacks access.
3. The original V2.7 `/proc` process scan reported zero candidates due to an inherited shell `set -f` glob-expansion defect. **Discard that zero count as evidence about processes.** V2.7.1 fixed the defect and passed operator Fedora synthetic checks **53/53**. On the actual ASUS the corrected read-only scan read UID fields for **153/153 sampled processes** with zero matching target-owner UID fields in that one snapshot. It cannot rule out a later process or effective owner-write access.
4. V2.8 matched each of the exact, project-defined root-Cron jobs once. The `AsusEdgeDNSGuard` target reported `NONROOT_UID_GID_OWNER_WRITE_YES`; `AsusEdgeWebUIStatus` reported `ROOT_ROOT_OWNER_WRITE_YES`. This **attributes the abnormal current owner class to DNS Guard**, not to the WebUI status collector; it does not attest source origin/history or imply code compromise.
5. An explicitly approved, read-only SHA-256 comparison on the router found the live DNS Guard script matched the historical reviewed source at PR #197 merge commit `01d6a7e00530ee8e9212820456047e2dee71a0a9`:
   - expected and observed SHA-256: `ecd44c59532073d33290b8eb500144e12ecfb4537542bc58a4c75be8753ab0db`;
   - `DNS_GUARD_SOURCE_COMPARISON=MATCH`, `FILES_MODIFIED=NO`, `SERVICES_MODIFIED=NO`.
   
   This establishes **byte-for-byte equality at the audit time**, not historical installer provenance, continuous file immutability, or secure owner/mode.

The live `/jffs/scripts/services-start` startup hook was separately observed on October 15 with an atypical numeric owner; **do not equate that separate hook with the direct Cron DNS Guard target** without further evidence.

## 2. Source/installation ownership hypothesis

The repository's [`router/scripts/services-start`](../../router/scripts/services-start) registers both named Cron jobs. [`scripts/install.sh`](../../scripts/install.sh) requires root, but its `install_file` implementation writes an existing destination with `cp "$src" "$dst"` and `chmod "$mode" "$dst"`; it does **not** explicitly normalize the resulting owner/group with `chown`. Independent isolated GNU/BusyBox copy tests demonstrated that a pre-existing foreign-owned destination can preserve UID/GID across overwrite. This is a **plausible cause** of persistent ownership drift, not evidence that this particular live installation followed that history.

Do **not** use the generic installer as a quick repair; it can also replace customized JFFS hooks and interfere with the independent SSD/RouterCloud work.

## 3. Fedora-only owner-repair research

| Lab | Operator Fedora result | Established within the synthetic scope | Explicitly unproven |
| --- | --- | --- | --- |
| V0.1 | **22/22 PASS** | Atomic replacement and injected failure/rollback model; unsafe paths/permissions rejected | Hardlink snapshot independence, real owner root:root, JFFS2 recovery |
| V0.2 | **26/26 PASS** | Independent private byte-copy backup; old-inode write does not change copied backup; copy-based rollback and negative tests | Live root-Cron process races; router filesystem durability |
| V0.3 | **9/9 PASS** | Open reader retains old inode; new open sees new inode; bounded simultaneous reads do not see a partial file; independent backup and rollback | Real ASUS `root:root`, JFFS2 power-loss durability, complete root Cron/writer concurrency |

A **separate assistant-only disposable Linux container** tested real kernel UID/GID/DAC behavior for synthetic files (**4/4 PASS**): a new root-owned 0755 file in a root-owned 0755 parent denied unprivileged writes/renames, while a file owned by an unprivileged user allowed that user to write. This is **not** an operator ASUS test. The operator V0.3 selftest explicitly reported `ACTUAL_ROOT_UID_GID_VERIFIED=NO`, `ROOT_CRON_PROCESS_RACE_EXHAUSTED=NO`, and `JFFS2_POWERLOSS_DURABILITY_VERIFIED=NO`.

V0.1's original hardlink rollback pointer is **not an independent backup**, since writes to the old inode via an already-open descriptor can affect the link. V0.2/V0.3 use separate verified backup bytes in the laboratory. Production rollback must not restore a root-executed script with the same unresolved nonroot ownership.
