## Grafana WAN-speed email alert

The monitoring path for degraded negotiated WAN speed was completed and merged
through PR #175.

The production rule `tuf_wan_speed_degraded` fires when the negotiated WAN
speed remains below 900 Mb/s for three minutes. The rule keeps
`noDataState: OK` so missing telemetry is not misreported as a WAN-speed
degradation event.

Live validation used a controlled threshold change while the real WAN link
remained at 1 Gb/s. Grafana transitioned through `Pending -> Firing`, delivered
a real email notification, then returned to `Resolved` after the production
threshold was restored. No physical WAN renegotiation or Internet outage was
introduced.

SMTP credentials remain outside Git. The repository contains only the
provisioned contact-point definition and environment-variable reference.

## Tailscale package/live-version drift hardening (#177)

Issue #177 was completed after the reference router demonstrated a real mismatch
between Entware package metadata and the live Tailscale binaries:

```text
Entware installed: 1.96.1-1
Entware candidate: 1.96.1-1
live tailscale:    1.102.3
live tailscaled:   1.102.3
```

The hardened maintenance path now:

- reads package metadata and the actual live CLI/daemon versions separately;
- compares versions deterministically and fails closed on malformed input;
- refuses an implicit downgrade before package mutation;
- records executable paths and SHA-256 provenance;
- verifies the running daemon image against the expected binary;
- preserves verified known-good rollback binaries plus a manifest before an
  allowed package transaction;
- forces a controlled daemon restart only during an explicit updater
  transaction;
- keeps Tailscale automatic update application disabled so package changes
  cannot bypass the project maintenance path;
- verifies that policy from the project healthcheck.

The real reference-router negative test detected the older Entware candidate
and exited with `RC=2` before mutation. The live CLI/daemon versions and
SHA-256 values were unchanged afterward.

Post-test validation confirmed:

```text
Tailscale status: PASS
exit-node advertisement: present
HEALTHCHECK_RC=0
Summary: 0 failure(s), 0 warning(s)
```

The positive newer-candidate path is covered by deterministic transaction
mocks. A real positive package upgrade is intentionally not claimed because the
active Entware feed still offers an older package than the validated live
binary.

The new CI coverage includes:

- newer candidate allowed;
- equal candidate no mutation;
- older candidate rejected;
- malformed/unknown version fail closed;
- service-recovery failure propagation;
- healthcheck failure propagation;
- automatic-update policy persistence.

A CI fixture was updated so the existing recovery suite also models the new
`AutoUpdate.Apply` health contract.

## Android Pi-hole / Tailscale policy and management reconciliation (#152 / PR #182)

Issue #152 advanced from design into a live-validated transport and DNS-enforcement
implementation for a selected Android client.

The new opt-in policy adds a source-scoped Pi-hole path for selected Tailscale
IPv4 sources. Matching TCP/UDP 53 traffic is DNATed to the dedicated Pi-hole
listener before the historical generic Tailscale DNS REDIRECT fallback.
Non-matching tailnet clients therefore keep the existing dnsmasq -> Unbound
path, while the selected client remains visible to Pi-hole under its original
Tailscale source identity.

The target mobile validation was intentionally bounded to:

```text
Wi-Fi:      OFF
LTE/5G:     ON
Tailscale:  ON
Exit node:  OFF
```

Live checks confirmed a fresh unique DNS marker in Pi-hole analytics, successful
internal RouterCloud name resolution, a known advertising domain blocked by
Pi-hole Gravity, RouterCloud reachability, and ASUS management access through
the supported hostname.

The same troubleshooting session exposed two separate management-path defects:

- RouterCloud is bound to a router-local alias, so Tailscale access terminates in
  INPUT rather than FORWARD. An explicit admin-scoped INPUT rule was added.
- ASUS WebUI was exposed externally on TCP/8443 while the real httpds listener
  remained on TCP/443. The policy now models the external and target ports
  separately and DNATs authorized Tailscale TCP/8443 traffic to the router LAN
  listener on TCP/443.

The healthcheck was extended to verify the source-scoped DNAT, post-DNAT INPUT
rule and actual HTTPS listener. Dedicated Pi-hole, RouterCloud and router-HTTPS
contract tests cover both valid and drifted rules.

The first GitHub Actions run for PR #182 revealed one repository-fixture gap:
the Python recovery test did not model the newly required router TCP/443
listener. Production behavior was already correct; the recovery fixture was
updated in commit `60439d7`, after which the aggregate validation suite passed.

During the live rollout, private service-portal URL keys were also found missing
from the local router configuration after configuration normalization. Only the
private `EDGE_PORTAL_*` values were restored from a pre-change backup; the
working Pi-hole, Tailscale, RouterCloud and firewall settings were not rolled
back. The Personal Cloud portal target was then configured locally. Deployment-
specific URLs and addresses remain outside the public repository.

Public documentation now includes:

- [Android global DNS filtering through Pi-hole and Tailscale](../android-pihole-tailscale-policy.md);
- [Android DNS Enforcement and Remote Management over Tailscale](../case-studies/android-tailscale-pihole-debugging.md);
- [sanitized issue #152 live validation](../../evidence/2026-10-06/issue-152-android-pihole-tailscale-validation.md).

Issue #152 remains open. The transport and source-scoped DNS path are validated,
but the stronger Pi-hole per-device group/list policy and final banking/payment
application compatibility checks are intentionally still pending.
