## 1. Oct 14 accepted DAC changes versus Oct 15 reboot baseline

- On Oct 14, the operator explicitly authorized a **bounded, nonrecursive live DAC Stage 1**: `ROUTER_DATA` physical mount root `0777 -> 0755` and `.routercloud-system` `0777 -> 0700`. Browser functions, service health and a scheduled restic backup passed within that acceptance scope; see [Oct 14 worklog](2026-10-14.md).
- On Oct 15, read-only inspection found **both physical ext4 SSD mount roots** (`ROUTER_DATA` and `ENTWARE`) again owned root:root, mode **0777** after boot/mount. Protected descendants were retained: `RouterCloud` root:root `0700` and `ENTWARE/entware` root:root `0755`. There was one active swap entry under **each** volume.
- Matching GNUton firmware source attempts `chmod(mountpoint, 0777)` on successful mount before dispatching `post-mount`. This is a source-supported explanation plus live mode observation, not a kernel audit trace. The historical Oct 14 PASS does **not** establish reboot persistence.
- A nonsticky `0777` mount-root ancestor exposes child **directory-entry** integrity to unprivileged local users, even when the child data directory itself is `0700`. This is a local integrity finding, not proof of remote compromise.

## 2. Draft PR #245: offline persistent repair design

- Draft helper is allowlisted to the two exact ext4 mount roots; requires verified filesystem identity via **private UUID** values, root ownership, expected mode, unique `/proc/mounts` record and firmware-native tools; attempts only a **nonrecursive `0777 -> 0755`** on accepted targets. Unrecognized state is refused.
- Actual GNUton `blkid` formatting, restricted PATH and firmware-native `/bin/busybox`, `/usr/bin/awk`, `/sbin/blkid`, `/bin/chmod` were checked on the running router; early-boot availability remains unproven.
- Both private UUID files were staged **only on Fedora**, privately owned, with directory `0700`, files `0600`, unique canonical values and manifest SHA parity. Actual UUIDs were not disclosed or committed.
- Updated post-mount insertion validates numeric root:root metadata for trusted JFFS ancestors, private UUID directory/file and helper, rejects symlinks and unsafe modes; **swap-before-AMTM is preserved even when the guard is NOT_READY**. Isolated composed tests and CI on the candidate passed.
- A fresh **V3 private Fedora-only post-mount candidate** passed exact pinned-snippet byte comparison, source/original hash, `sh -n`, manifest checks and a separate **Fedora-only** same-directory atomic replace/restore simulation. The live ASUS `post-mount` original remained root:root `0755`, ordinary non-symlink, and matched its known saved SHA in independent read-only checks.
- **Not established:** actual JFFS payload delivery and root ownership, safe JFFS atomic activation/recovery, early `post-mount` execution, post-reboot persistence or complete compatibility of SSD-root writers. No helper/private UUID insertion has been installed on the router.

See Draft PR #245's [GO/NO-GO](https://github.com/wojko6/Advanced-ASUS-Edge-Gateway-ZTNA-Infrastructure/blob/security/issue235-ssd-mount-mode-post-mount-lab-20261015/docs/issue235-production-go-no-go-2026-10-15.md) and [scoped staging/rollback runbook](https://github.com/wojko6/Advanced-ASUS-Edge-Gateway-ZTNA-Infrastructure/blob/security/issue235-ssd-mount-mode-post-mount-lab-20261015/docs/issue235-jffs-staging-activation-rollback-runbook-draft.md). These are **DRAFT documents**, not production authorization.
