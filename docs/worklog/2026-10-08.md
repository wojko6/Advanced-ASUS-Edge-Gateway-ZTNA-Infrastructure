## RouterCloud backup/maintenance monitoring recovery

An early automatic RouterCloud backup attempt failed while the Fedora host
was not yet connected to Wi-Fi. The next scheduled backup succeeded after
network connectivity returned; backup storage and the Restic repository were
present and the prior maintenance run reported success.

Backup and maintenance outcome metrics were recovered in VictoriaMetrics
without rerunning backup maintenance. Grafana's four RouterCloud rules were
then checked through its runtime API:

- `routercloud_backup_bad`;
- `routercloud_backup_stale`;
- `routercloud_maintenance_bad`;
- `routercloud_maintenance_stale`.

Result: **4/4**, all `state=inactive`, `health=ok`.

A reversible Fedora user-service override increased RouterCloud backup's
maximum router-network readiness wait from 90 to 300 seconds (5-second retry
interval). The override and active six-hour timer survived a subsequent host
reboot. The new wait path still requires observation during a future delayed
network startup; it has not been fault-injected.

## Fedora Wi-Fi availability investigation

The Fedora host uses the Realtek `rtw89_8852ae` wireless driver.
An early boot showed delayed Wi-Fi autoconnection and overlapping scan
warnings. Prior boots connected promptly; therefore the slow start is
intermittent rather than an established constant delay.

A separate reconnection incident attempted the saved 2.4 GHz profile but
failed with `no-secrets`. The 2.4 GHz credential was saved locally, with
both 2.4/5 GHz autoconnect profiles retained and Wi-Fi power-saving confirmed
disabled. No wireless credential was committed.

A subsequent reboot connected to 5 GHz approximately 17 seconds after system
boot with no reported pending-scan warnings. The underlying intermittent
driver/scanning cause is **not yet proven resolved**.
