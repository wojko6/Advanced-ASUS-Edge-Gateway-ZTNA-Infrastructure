## GeForce NOW follow-up

A same-session overlay snapshot with the exit node off showed:

```text
server:      Poland (NP-WAW-01)
ping:        13 ms
packet loss: 0
frame loss:  0
```

A later snapshot while the ASUS exit node was active showed:

```text
server:      Poland (NP-WAW-01)
ping:        12 ms
packet loss: 0
frame loss:  0
```

A third snapshot initially intended as the return-to-baseline A2 segment
showed 11 ms / zero loss, but route verification later proved the exit node
was still selected. The A/B/A sequence is therefore confounded and is not
used to claim an exit-node performance effect.

During an active Exit Node session, a 15-second client-side UDP
conversation summary observed approximately:

```text
72,708 packets
79 MB
```

between the Fedora client and ASUS Tailscale transport endpoints. This
explained the dominant local encrypted flow but did not localize any
application packet loss.

After the exit node was fully disabled, the operator continued normal
GeForce NOW use over Ethernet for approximately one hour.

Observed during that period:

```text
application packet loss: 0
ping: stable
wired path: stable
```

The Zen endpoint blocker was toggled on/off during normal use without an
observed difference in the GeForce NOW loss or latency behaviour.

This does not prove that Zen can never affect GeForce NOW. It does make Zen
a weaker explanation for the earlier intermittent symptom in the observed
window.

The existing Ethernet/Wi-Fi case study remains bounded: earlier controlled
evidence showed zero packet loss in the documented Wi-Fi run but materially
higher Wi-Fi jitter and rare local-path latency excursions. A future loss
localization run should change only the transport and capture the same
stream concurrently at the client and router when the symptom is actually
reproduced.
