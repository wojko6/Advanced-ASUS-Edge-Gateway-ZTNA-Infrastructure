# Worklog — 2026-09-28

## Pi-hole main-LAN adoption

The reference main LAN completed the staged migration from Diversion to Pi-hole
FTL on the ASUS TUF-AX5400.

The accepted resolver split is:

```text
DHCP-managed main-LAN clients -> Pi-hole FTL -> Unbound
firmware dnsmasq -> Unbound for DHCP/local naming support and existing
classic-DNS interception/Tailscale listener paths
```

The migration evidence covers the dedicated Pi-hole listener, OISD parity,
query-history visibility, DHCP cutover, reverse DNS, duplicate-service cleanup
and final reboot validation.

## Startup reliability

A cleanup reboot exposed that the active `post-mount` hook had lost the actual
`swapon` action. Both swap files existed but were inactive, and Tailscale
failed with a Go-runtime out-of-memory allocation error.

Explicit per-volume swap activation was restored before AMTM/Entware startup.
The subsequent clean reboot returned swap, Tailscale, Pi-hole, Unbound and the
main-LAN DNS policy automatically.

The consolidated design is documented in
[Swap and Memory Reliability](../swap-and-memory-reliability.md).

## Documentation alignment for issue #108

The DNS/client-activity analytics plan was reviewed after Pi-hole became the
active main-LAN filtering layer.

The previous concept of using broad dnsmasq query logging as the primary
analytics source was superseded. The new design uses the existing Pi-hole FTL
query-history database as the preferred read-only source and keeps collection
state, Loki, Alloy, retention and Grafana processing on Fedora.

The first accepted dataset is intentionally limited to traffic that actually
traverses Pi-hole. Existing dnsmasq interception/Tailscale paths and encrypted
DNS remain explicit coverage gaps until separately measured.

Issue #108, the roadmap, project status, operations guidance, README and DNS
architecture documentation were reconciled around this model.

## Issue #108 Phase 0 — PASS

The read-only Pi-hole analytics preflight was completed against the deployed
Pi-hole v6 build.

Validated points:

1. the supported Pi-hole API exposes the required query metadata;
2. unauthenticated query-history access returns HTTP 401 after enabling the
   normal Pi-hole password;
3. a separate application password authenticates successfully with
   `webserver.api.app_sudo=false`;
4. Fedora reaches the HTTP API through a loopback-only SSH local forward;
5. RAM and `disk=true` query-history reads are both available;
6. the response-level cursor was proven unsafe as the first disk snapshot
   cursor when fresh queries have not yet flushed to SQLite;
7. a bounded 100-row extraction produced no material RAM/swap/load pressure in
   the measured sample.

The cursor test observed a 13-query RAM/disk head gap. The accepted design
therefore freezes each source on the first query ID actually returned, unions
the disk and memory snapshots on Fedora, deduplicates by query ID and advances
the checkpoint only after successful local persistence.

Sanitized evidence:
[`evidence/2026-09-28/pi-hole-api-phase0-preflight.md`](../../evidence/2026-09-28/pi-hole-api-phase0-preflight.md).

## Issue #108 Phase 1 implementation

A first Fedora collector implementation was added under `monitoring/`.

The collector:

- uses the Pi-hole v6 authenticated API rather than opening the live SQLite DB;
- refuses cleartext non-loopback HTTP for credentials;
- reads its application password from a private file rather than the public
  configuration example;
- combines disk and in-memory snapshots using source-local cursors;
- deduplicates by query ID;
- writes private NDJSON suitable for later Alloy/Loki ingestion;
- journals each output batch so a crash between append and checkpoint update can
  be recovered without blindly duplicating the batch;
- fails closed on unexpected schema changes.

Systemd user units provide the loopback SSH tunnel, one-shot collector and
one-minute timer. Unit tests cover the disk/global-cursor edge case,
RAM/disk deduplication, crash recovery and loopback-only cleartext policy.

The live Fedora deployment is now validated. The first run exposed a
first-append file-creation bug, fixed in PR #120; the prepared-batch journal
then recovered the staged batch automatically. Repeated manual and timer-driven
runs preserved a strictly ascending, duplicate-free query-ID stream.

A controlled SSH-transport outage returned RC=1 without changing the accepted
event count or checkpoint. After the tunnel was restored, the collector caught
up from the combined disk/in-memory Pi-hole views. The final checkpoint had
10,414 events, 10,414 unique IDs, zero duplicates and a checkpoint equal to the
maximum persisted ID.

Sanitized live evidence:
[`evidence/2026-09-28/pi-hole-dns-collector-live-validation.md`](../../evidence/2026-09-28/pi-hole-dns-collector-live-validation.md).

Loki/Alloy integration, longer-term storage/retention measurement and the
Grafana DNS dashboard remain the next steps.


## 5 GHz non-DFS startup optimization

The normal-use 5 GHz profile was simplified after the earlier HE160
interoperability work:

```text
channel:       36
channel width: 20/40/80 MHz
160 MHz:       disabled
Wi-Fi mode:    HE / 802.11ax
```

The previous profile used channel 100 with 160 MHz enabled, which placed the
radio in DFS operation. A controlled router restart was performed after the
change. The operator observed that the 5 GHz network became available
noticeably faster after reboot.

No exact startup time was measured, so this is not presented as a quantitative
before/after benchmark. The observation is consistent with removing DFS/CAC
startup delay from the normal-use profile.

This change also preserves the HE80 operating mode that produced the strongest
and most stable MT7922 throughput during the earlier Wi-Fi interoperability
tests. It does not change the historical HE160 evidence or imply that DFS caused
the MT7922 HE160 throughput defect.
