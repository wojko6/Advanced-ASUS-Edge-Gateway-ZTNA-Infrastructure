# 2026-09-26 Engineering Worklog

## Scope

This session focused on a Wi-Fi 6 HE160 performance anomaly on the ASUS
TUF-AX5400 reference environment.

The goal was to determine whether poor 160 MHz throughput was:

- a generic ASUS/Broadcom HE160 limitation;
- a Windows/MediaTek MT7922 behavior;
- a client-specific interoperability problem;
- or a more general LAN/server bottleneck.

The session remained separate from the project's router security-policy
validation. No new firewall, Tailscale, DNS, logging or recovery claim was
derived from the Wi-Fi throughput tests.

## Controlled runtime HE160 enablement

The 5 GHz radio could be configured as `100/160` while the operational
chanspec remained `100/80`.

A temporary controlled test changed the related NVRAM variables together:

```sh
nvram set wl_bw_switch_160=0
nvram set wl0_bw_switch_160=0
nvram set wl1_bw_switch_160=0
```

No `nvram commit` was performed.

After the wireless subsystem was restarted, the operational 5 GHz chanspec
changed to `100/160`.

Because all three related variables were changed together, the test supports
only the bounded conclusion that the `bw_switch_160` mechanism family affects
runtime HE160 behavior in this firmware state. It does not identify one
individual key as independently causal.

## Windows MT7922 baseline and driver comparison

The Windows client used a MediaTek Wi-Fi 6E MT7922 2x2 adapter.

Two driver revisions were compared:

```text
old:     3.3.0.918
current: 26.40.2.587
```

The current driver established a 2x2 HE160 association with a reported PHY rate
of approximately 2402/2402 Mb/s under strong-signal conditions.

### Current-driver HE80

Representative 120-second, four-stream iperf3 results:

```text
client -> LAN: approximately 880 Mb/s receiver
LAN -> client: approximately 856 Mb/s receiver, 0 TCP Retr
```

This established a healthy same-client HE80 control and strongly reduced the
likelihood of a generic wired-server or 100 Mb/s LAN bottleneck.

### Current-driver HE160

Representative results:

```text
client -> LAN: approximately 74.7 Mb/s receiver
LAN -> client: approximately 401 Mb/s receiver, 3,872 TCP Retr
```

The association remained at 160 MHz / 2 spatial streams with a high negotiated
PHY rate, so the application-throughput collapse was not explained by a low
link rate alone.

### Old-driver HE160

The earlier driver also showed poor HE160 behavior:

```text
client -> LAN: approximately 53.2 Mb/s receiver
LAN -> client: approximately 339 Mb/s receiver, 5,410 TCP Retr
```

The newer driver improved the symptom but did not eliminate the HE80/HE160 gap.
The evidence therefore shows driver sensitivity without proving that the
Windows driver is the sole root cause.

## Independent Android HE160 reference

An independent Android 2x2 client was then tested on the same ASUS 5 GHz radio
at 160 MHz.

Representative results:

```text
Android -> LAN: 707 Mb/s sender / 706 Mb/s receiver, 20 TCP Retr
LAN -> Android: 673 Mb/s sender / 671 Mb/s receiver, 404 TCP Retr
```

During the active tests the router telemetry remained at 160 MHz / 2 spatial
streams with strong RSSI.

This substantially higher throughput on the same HE160 radio strongly weakens a
simple "ASUS HE160 is globally broken" explanation.

## Router-side telemetry interpretation

Broadcom `wl sta_info` counters were sampled throughout the tests.

The Android runs demonstrated that large increases in the router-side
`rx total pkts retried` counter could coexist with approximately 670–706 Mb/s
of TCP throughput and far smaller iperf3 TCP retransmission counts.

The project therefore treats these Broadcom retry-related values as
station-associated wireless telemetry only. They are not relabeled as exact TCP
loss or as a one-to-one count of application retransmissions.

## Final measured state

At the end of the measurement phase, the 5 GHz radio reported:

```text
runtime interface:       eth6
configured chanspec:     100/160
runtime chanspec:        100/160
DFS state:               In-Service Monitoring
DFS channel:             cleared
bw_switch_160 family:    0 / 0 / 0
```

The `bw_switch_160` state remained part of the temporary uncommitted
experiment. It was not promoted into a persistent project configuration by this
session.

## Assessment

The evidence supports a bounded interoperability assessment:

> Severe throughput degradation is strongly associated with HE160 operation in
> the tested MediaTek MT7922 ↔ ASUS/Broadcom combination.

The session does not prove a universal defect in the MT7922, the MediaTek
Windows driver, ASUS firmware or Broadcom HE160 behavior.

The independent Android comparison is especially important because it shows
that another 2x2 client can sustain much higher throughput on the same ASUS
HE160 radio.
