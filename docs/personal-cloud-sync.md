# Personal Cloud one-way sync

Issue #136 implements an auditable one-way synchronization path from a Fedora workstation to the dedicated `ROUTER_DATA` filesystem on the ASUS router.

## Validated design

```text
Fedora ~/RouterCloud/
        |
        | rsync -rtv over SSH/1122
        | dedicated client key
        v
Dropbear forced command
        |
        v
/jffs/addons/asus-edge/bin/personal-cloud-rsync
        |
        | exact allowlist of rsync --server commands
        v
/tmp/mnt/ROUTER_DATA/RouterCloud/
```

Version 1 deliberately does **not** use `--delete`. Removing a local file does not remove an already synchronized copy from the router SSD.

The Fedora side consists of:

- `scripts/routercloud-sync.sh`;
- a dedicated Ed25519 identity at `~/.ssh/id_ed25519_routercloud` by default;
- `routercloud-sync.path` for low-latency top-level directory-change triggers;
- `routercloud-sync.timer` for five-minute full-tree reconciliation;
- `flock` to prevent overlapping runs;
- `~/.local/state/routercloud-sync/status.env` for the last result.

The router side uses `router/scripts/personal-cloud-rsync` as a fail-closed forced-command wrapper.

## SSH identity isolation

The client intentionally prevents fallback to the workstation's ordinary SSH identities. The validated SSH command includes:

```text
-F /dev/null
-o IdentityFile=none
-i ~/.ssh/id_ed25519_routercloud
-o IdentitiesOnly=yes
-o IdentityAgent=none
-o BatchMode=yes
-o PasswordAuthentication=no
-o KbdInteractiveAuthentication=no
-o PreferredAuthentications=publickey
-o StrictHostKeyChecking=yes
```

This matters because `IdentitiesOnly=yes` by itself did not stop OpenSSH from trying the default `~/.ssh/id_ed25519` identity when the dedicated key file was temporarily removed. The final client configuration was negative-tested with the dedicated key absent and failed with SSH return code 255.

## Router-side restriction

The dedicated public key is persisted with one forced command:

```text
restrict,command="/jffs/addons/asus-edge/bin/personal-cloud-rsync" ssh-ed25519 <PUBLIC_KEY> personal-cloud-rsync
```

Do not publish the private key, complete `sshd_authkeys` value, or raw key material.

The wrapper accepts only the exact rsync server command generated by the validated `rsync -rtv --rsync-path=/opt/bin/rsync` client for the dedicated RouterCloud path, plus the matching dry-run form. Arbitrary commands return exit code 126.

The acceptance work briefly evaluated Entware `rrsync`. It was useful diagnostically, but it is **not** part of the final data path. The existing project wrapper is stricter because it allowlists the exact command and destination used by this deployment.

Do not layer a second `command=` option onto the same public-key record. A test configuration that combined the existing wrapper command with a second `rrsync` forced command was rejected by Dropbear after SSH-key regeneration. The final persistent record contains one forced command only.

## Router preparation

The reference deployment requires Entware rsync and a dedicated destination:

```sh
/opt/bin/opkg install rsync
mkdir -p /tmp/mnt/ROUTER_DATA/RouterCloud
chmod 0700 /tmp/mnt/ROUTER_DATA/RouterCloud
```

Install the wrapper:

```sh
install -m 0755 router/scripts/personal-cloud-rsync \
  /jffs/addons/asus-edge/bin/personal-cloud-rsync
```

Persist the dedicated public key through the router's SSH-key mechanism while preserving existing administrator keys. On the validated Asuswrt-Merlin deployment, the persistent key material is mirrored through `/jffs/nvram/sshd_authkeys` and materialized into the runtime `authorized_keys` file. Revalidate both ordinary administrator SSH and the restricted key after an SSH restart and after a full router reboot.

## Fedora installation

```sh
mkdir -p ~/.local/bin ~/.config/systemd/user

install -m 0700 scripts/routercloud-sync.sh \
  ~/.local/bin/routercloud-sync

install -m 0644 config/systemd/routercloud-sync.service \
  ~/.config/systemd/user/

install -m 0644 config/systemd/routercloud-sync.path \
  ~/.config/systemd/user/

install -m 0644 config/systemd/routercloud-sync.timer \
  ~/.config/systemd/user/

systemctl --user daemon-reload
systemctl --user enable --now routercloud-sync.path routercloud-sync.timer
```

Reference defaults:

```text
source:      ~/RouterCloud/
host:        192.168.50.1
user:        admin1
SSH port:    1122
identity:    ~/.ssh/id_ed25519_routercloud
destination: /tmp/mnt/ROUTER_DATA/RouterCloud/
```

The client supports overrides through `ROUTERCLOUD_SOURCE`, `ROUTERCLOUD_HOST`, `ROUTERCLOUD_USER`, `ROUTERCLOUD_SSH_PORT`, `ROUTERCLOUD_DEST`, and `ROUTERCLOUD_KEY`. Any destination change also requires a deliberate server-wrapper review because the wrapper is intentionally destination-specific.

## Operations

Inspect the latest result with:

```sh
cat ~/.local/state/routercloud-sync/status.env
journalctl --user -u routercloud-sync.service --no-pager
systemctl --user status routercloud-sync.path
systemctl --user list-timers routercloud-sync.timer --all
```

A successful run records `LAST_RESULT=success` and `LAST_RC=0`. A transport/authentication failure records the nonzero return code.

`systemd.path` is an acceleration mechanism, not the sole correctness mechanism. It is not a recursive watch of every future nested directory. The five-minute timer remains enabled as the authoritative reconciliation fallback.

## Security and behavior boundaries

- no new WAN-facing file-sharing service is introduced;
- the automation key cannot obtain an interactive shell in the validated state;
- the client does not fall back to ordinary workstation SSH identities;
- v1 does not propagate deletions;
- `-rtv`, rather than archive mode, avoids copying Fedora UID/GID ownership;
- transport failure is fail-closed for new data transfer;
- the path/timer workflow was validated after a full router reboot;
- versioned history, snapshots, browser access, and Grafana status are separate follow-up work.
