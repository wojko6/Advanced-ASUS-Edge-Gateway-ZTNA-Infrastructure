# Requirements and acceptance map

**Status:** CURRENT — reference deployment and planned validation

**Reviewed:** 2026-10-07

This map links the existing architecture and test procedures to the reference ASUS TUF-AX5400. The status applies only to the stated test date and path. It does not turn a roadmap proposal, a mock test, or an operator-reported observation into independently captured live evidence. For the latest deployment summary see [project status](../PROJECT-STATUS.md); for detailed test methods see [testing](testing.md).

## Roles and use cases

| Role | Intended use | Boundary |
| --- | --- | --- |
| Authorized admin device | Open the router HTTPS panel through Tailscale | Tailscale authorization, exact router firewall source rule and router login |
| Ordinary tailnet device | Use only approved destinations or exit-node access if entitled | No router management; selected LAN destinations are locally source/destination scoped. Exit-node entitlement is enforced by Tailscale Grants while router-local exit-node source scoping remains open under #176. |
| LAN client | Resolve classic DNS through the router | Main-LAN DHCP advertises Pi-hole; firmware dnsmasq retains local naming and the existing intercepted classic-DNS path; both use Unbound upstream |
| Router operator | Back up, verify, deploy, check health and recover configuration | Local/LAN access and private recovery copies remain necessary |

## Functional acceptance

| ID | Requirement and observable pass condition | Method / current evidence | Current limit |
| --- | --- | --- | --- |
| F-01 | Only configured admin Tailscale IPv4 sources can reach router HTTPS; from an authorized client the panel loads with its DNS-name certificate verified. | Exact input/DNAT rules plus authorized and unauthorized client probes per [security matrix](testing.md#router-and-remote-client-security-matrix). Fedora verified TLS and Android operator-reported login after the 2026-09-23 reboot are in the [worklog](worklog/2026-09-23.md); the separate unauthorized-client denial is captured in the [sanitized live evidence](../evidence/2026-09-23/unauthorized-tailnet-management-denial.md). | **Validated for the tested 2026-09-23 reference deployment:** the unauthorized client reached the router as a Tailscale peer but could not establish TCP/8443; five scoped NEW TCP/8443 packets were correlated with the temporary counter-only rule and then the production deny tail. Revalidate after admin-source, Tailscale-policy, firewall, or firmware changes. The phone-browser certificate verdict remains client-specific and was not recorded. |
| F-02 | Classic IPv4 UDP/TCP 53 entering on the specified LAN/Tailscale interfaces follows the router DNS path; DNSSEC validation works at Unbound. | [2026-09-27 current-firmware AUDIT-03 revalidation](../evidence/2026-09-27/audit-03-current-firmware-dns-datapath-revalidation.md) correlated controlled Fedora UDP/53 and TCP/53 traffic through `tailscale0 -> EDGE_TS_PREROUTING -> REDIRECT :53 -> dnsmasq -> Unbound 127.0.0.1:53535`, with exact managed counter deltas and matching loopback resolver traffic. | **Validated for the tested current-firmware classic IPv4 path.** DoH/HTTPS, DoQ/QUIC, VPN-carried DNS, application-specific encrypted resolvers and IPv6 resolver paths remain outside this requirement. |
| F-03 | An entitled Tailscale client can use exit-node IPv4 routing only through the selected WAN path, with platform NAT and return handling present. | [2026-09-23 post-firmware packet correlation](../evidence/2026-09-23/audit-02-post-firmware-exit-node-revalidation.md) validated the before/after-NAT path on GNUton `3004.388.11_1-gnuton1_tuf`; the [2026-09-27 Android validation](../evidence/2026-09-27/issue-67-android-exit-node-public-ip-validation.md) reconfirmed the expected client public-IP behavior; the later 2026-10-06 Tailscale 1.103.375/DNS Guard work reconfirmed exit-node runtime after upgrade. | **Validated for the tested IPv4 datapath.** Local source-scoped exit-node authorization is not yet implemented; Tailscale Grants currently carry that entitlement boundary and #176 tracks the independent local allowlist. Revalidate after material firmware/firewall/routing changes. |
| F-04 | On a clean startup the required SSD mounts, swap and project services are available; WPS remains off and unnecessary USB-service listeners are closed. | The [2026-09-27 startup/persistence evidence](../evidence/2026-09-27/issue-66-clean-startup-persistence-evidence.md) records three fresh clean startup cycles after correcting the pre-Entware swap ordering, building on the earlier reboot/USB-exposure checkpoints. | **Validated for the current reference startup path.** AMTM ownership of `post-mount` remains an operational boundary and must be rechecked if the addon rewrites the hook. |
| F-05 | A project backup passes its sidecar hash and internal manifest checks; restore dry-run accepts it; a controlled failure during restore attempts rollback. | [Router DR baseline](router-disaster-recovery.md) and [2026-09-27 clean-room restore evidence](../evidence/2026-09-27/issue-100-dr-cleanroom-restore-validation.md): off-router sidecar verification, internal manifest validation, dry-run, alternate-root apply, byte-for-byte JFFS/opt comparison, permission-mode comparison and backward-compatible `post-mount` safety all passed. | The project archive intentionally excludes Tailscale authentication/state and is not a firmware image. Native NVRAM/settings recovery remains a separate private artifact, and measured RTO/RPO are not yet claimed. |
| F-06 | Main-LAN DHCP clients receive only the dedicated Pi-hole resolver; Pi-hole forwards allowed external queries to Unbound, preserves DNSSEC negative behavior, and resolves active local DHCP names through conditional reverse DNS. | [2026-09-28 main-LAN cutover evidence](../evidence/2026-09-28/pi-hole-main-lan-cutover-validation.md) records DHCP renewal, Pi-hole blocking, Unbound DNSSEC behavior, reverse DNS, duplicate-service removal and final reboot persistence. | **Validated for the main-LAN DHCP path.** Selected Tailscale classic-DNS sources can now be DNATed to Pi-hole, while non-selected generic Tailscale interception still falls back to firmware dnsmasq. The separately validated exit-node system-resolver path reaches Pi-hole only in DNS Guard healthy steady state. |
| F-07 | DNS activity analytics for the Pi-hole-visible main-LAN dataset are collected read-only, processed off-router, distinguish at least two controlled clients, avoid high-cardinality client/domain Loki labels, and state resolver-coverage gaps explicitly. | [Issue #108 plan](network-dns-visibility-client-activity-analytics.md) plus [Phase 2/3 validation](../evidence/2026-09-28/pi-hole-dns-analytics-phase2-3-validation.md) cover the Pi-hole FTL source, Fedora collector, Alloy/Loki/Grafana pipeline, reboot persistence, two-client acceptance and the tested Tailscale coverage boundary. | **Live-validated for the tested Pi-hole-visible main-LAN path.** Two controlled clients were distinguishable, high-cardinality client/domain values were not persistent Loki labels, and the tested Tailscale classic-DNS path was confirmed absent from Pi-hole history. Longer-term retention/storage, rollback/uninstall and hard-coded external LAN interception correlation remain open. |

| F-08 | Router system DNS must boot without a Pi-hole/Unbound/NTP dependency cycle, fail open to current WAN bootstrap DNS when the local resolver stack is unhealthy or break-glass is active, and promote to Pi-hole only after the complete local path is healthy. | [DNS Guard v3.1 production validation](../evidence/2026-10-06/dns-guard-v3.1-production-validation.md) covers controlled promotion/fallback, sticky break-glass, watchdog recovery, full cold boot and Android LTE exit-node DNS reaching Pi-hole. | **Validated for the reference router.** Fail-open intentionally bypasses Pi-hole filtering during local-DNS failure; encrypted application DNS remains outside the claim. |
| F-09 | The documented public attack surface must be validated from independent LAN, Tailscale and genuine external-WAN vantage points before a closed/filtered claim is made. | [Port exposure and trust-boundary audit](case-studies/port-exposure-trust-boundary-audit-2026-10-07.md) correlates local listeners/firewall/NAT with full LAN TCP scanning, authorized/unauthorized Tailscale tests, Fedora source restrictions, verified mobile-Internet routing and selected public-IPv4 TCP probes. | **Validated for the tested 2026-10-07 surfaces.** Selected public-IPv4 TCP ports were filtered/time-out; native WAN IPv6 was disabled with no routable WAN IPv6 path. External WAN UDP was not conclusively tested and remains outside the claim. |
| F-10 | At least one actionable Grafana alert path must deliver both firing and recovered notifications out of band without storing SMTP credentials in Git. | The provisioned e-mail contact point and [WAN-speed e-mail validation](../evidence/2026-10-06/grafana-wan-speed-email-alert-validation.md) demonstrate firing/resolved delivery for the WAN-speed rule. | **Partially validated.** The e-mail transport/contact point is proven, but complete severity routing, RouterCloud Backup BAD, grouping/anti-flap and phone escalation remain open under #178. |

## Nonfunctional acceptance and risks

| ID | Goal / decision criterion | Current state |
| --- | --- | --- |
| N-01 | Treat credentials, node state and raw router evidence as private; only publish minimized, reviewed extracts. | [Publication checklist](evidence-collection.md#publication-checklist) applies; the 2026-09-23 raw backup/evidence copies remain private. |
| N-02 | Keep recovery copies in a separate failure domain, encrypted and integrity checked; define retention, backup monitoring, then measure recovery time/data loss in a drill. | #100 established verified off-router project backup copies plus a separately encrypted native ASUS/Merlin settings export and a successful clean-room restore for the pre-Pi-hole reference state. The 2026-09-28 Pi-hole adoption adds a documented current DR gap: Pi-hole/FTL service, dedicated alias/startup integration and filtering-policy reconstruction still require a new clean-room validation. Automated transfer/retention monitoring and measured RTO/RPO remain [planned](roadmap.md). |
| N-03 | Preserve the historical Diversion acceptance result while treating the later Pi-hole cutover as a separate migration decision. | **Historical baseline completed 2026-09-27; replaced on the main-LAN DHCP path 2026-09-28.** Diversion acceptance evidence remains valid for the tested historical state, while #80 documents the later Pi-hole adoption. |
| N-04 | Measure latency, loss, throughput and CPU/RAM before setting performance targets for this platform. | [Performance method](testing.md#performance-baseline) exists and the [GeForce NOW Ethernet/Wi-Fi case study](case-studies/geforce-now-ethernet-vs-wifi6-case-study.md) provides bounded real-time workload measurements. A later 2026-09-25 wired normal-use observation remained stable for approximately one hour, but no universal throughput, latency or availability objective has been accepted for the platform. |
| N-05 | Make availability claims match the real physical design; document single points of failure, power dependencies and the difference between HA and recoverability. | [Availability and redundancy](architecture/availability-and-redundancy.md) records the single gateway/WAN/storage/monitoring failure domains and marks FHRP/LACP/STP redundancy mechanisms as not applicable to the present topology. | No gateway HA, redundant WAN or validated UPS/power-continuity baseline is currently claimed. RTO/RPO remain unmeasured until a timed current-state DR drill. |
| N-06 | Define addressing and trust-zone ownership before implementing VLAN segmentation. | [Addressing and trust-zone plan](architecture/addressing-and-zones.md) records current address/service ownership and a design-only Trusted/IoT/Guest policy matrix. | VLAN IDs/subnets and inter-zone implementation remain planned under #143; the main LAN must not be described as already segmented. |

Pi-hole main-LAN filtering, the external monitoring baseline, centralized
logging, initial Grafana alerting and the Pi-hole-visible DNS analytics baseline
are now validated capabilities within their documented boundaries. Remaining
work in the [roadmap](roadmap.md) includes DNS-analytics retention/rollback and
LAN-interception coverage closure, the separate encrypted-DNS assessment,
the complete notification policy/mobile escalation and mobile telemetry; those items still require their own
failure cases and acceptance evidence before being described as complete. The e-mail contact-point transport itself now has bounded firing/resolved evidence.
