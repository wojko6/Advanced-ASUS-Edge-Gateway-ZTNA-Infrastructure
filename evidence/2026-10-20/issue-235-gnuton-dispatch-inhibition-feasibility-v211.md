# Issue #235 — V2.11 GNUton privileged-script dispatch / trusted publisher feasibility (2026-10-20)

> **Evidence and design review ONLY.** This is a **fresh review of the already committed project sources** and previously pinned GNUton dispatcher findings. **No new live ASUS source/binary inspection**, no extra synthetic test, no SSH or `cru`, no production file, NVRAM, permission or backup changes. `PRIVILEGED_EXECUTION_TRUST_GATE=HOLD`; `DEPLOYMENT_GATE=HOLD`.

## Question

Can we safely repair the observed **nonroot-owned owner-writable, root-run** `/jffs/scripts/services-start` (exact **full** hook) and `/jffs/addons/asus-edge/bin/dns-guard` using an existing, selective, power-interruption-resistant GNUton execution gate? Or could the publisher safely operate by only temporarily deleting Cron/holding a userspace lock?

**Verdict at this stage: neither method has been proven on the reference firmware.** The already verified V2.8 primary source copies and V2.9 same-filesystem observation allow security design work to continue; V2.10's optional extra physical backup remains **DEFERRED** by operator decision. Independent recovery remains a separate residual production-approval gap, not a mandate to run another backup now.

## Decision gates and meaningful next investigation

**A — trusted launcher / immutable approved source** (UNBUILT): a separately controlled root authority must authenticate exact source bytes and two-role `issue235-privileged-scripts-owner-repair` scope, then hold both protected staged inodes and object-to-publication identity. It must reject mutable same-UID basename, writable approval store, symlink/alias, unexpected hardlinks, mutation after verification, arbitrary target path and reuse of **SSD PR #245** signer/manifest. No root-owned publish tool exists yet. V2.7 approval design has **not** issued authorization.

**B — firmware run inhibition** (UNPROVEN): to claim a safe *unattended* transition, prove a selective inhibition that takes effect **before** root script dispatch (not inside the target script), covers firmware boot/manual `services-start`, minute Cron, direct WAN handler and operator break-glass while preserving independent DNS recovery, and survives interrupted publication/restart without executing old untrusted file. No such mechanism was found in the bounded reviewed source. Do not create a new JFFS `init-start`, run `cru d`/global script toggle or disable emergency DNS to simulate that proof.

**C — JFFS2 interruption/old writer semantics** (UNPROVEN): address original nonroot-owned inode and existing write-capable FDs, any already running root scripts, staging immutability, one-file-at-a-time cross-power-loss state and recovery on representative target JFFS2. No `flock`, user-owned marker, filesystem-independent `fsync`, name-only rename or postcheck is sufficient evidence of these properties.

**D — operator-supervised alternative** (DISCUSSION ONLY): if early boot inhibition cannot be provided by verified firmware, evaluate a separately approved *manually supervised* maintenance/recovery design and clearly document residual risk instead of pretending it is crash-safe. There is **no default downgrade of the NO-GO gate** merely because operation is manual, and no acceptance here of possible untrusted code execution at root after power loss.

**Recommended stop/review point:** avoid coding another synthetic approval parser or running user `chown` commands. The next useful technical evidence would be a bounded, exact-version **firmware dispatcher/launcher trust source and deployed binary equivalence** review, and then selecting either proven selective inhibition or a formally reviewed manual-only path with explicit residual risk and independent LAN/DNS recovery. Any live read-only ASUS probe would require separate coordination. Do not create backup/media work now.

## V2.12 follow-up — upstream `_eval` code actually retrieved

The [V2.12 exact-tag source report](issue-235-gnuton-firmware-launch-trust-boundary-v212.md) resolves V2.11's previously unverified **implementation** of `_eval`: GNUton `release/src/router/shared/shutils.c` at `3004.388.11_1-gnuton1` uses `fork()` then `execvp(argv[0], argv)`. The dispatcher checks `stat` on the target pathname before the fork; no same-FD execution or source digest/owner binding appears in the inspected chain. The tagged `cru` file locks crontab writes, not runtime dispatch. This is a source-only completion of a narrow V2.11 evidence gap; not a deployable fix or live binary verification.
